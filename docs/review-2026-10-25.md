## Speed

Nothing in the code or the docs uses `torch.compile`, an attention backend
other than PyTorch's default SDPA, or diffusers' step caches; the
2026-10-25 grep for each across `backend/`, `docs/` and `tests/` found
none. The measurements say there is room:

- Weight-only fp8 and int8 run *slower* a step than bf16 on every
  checkpoint measured all three ways (`docs/verified.md`, "Quantization and
  offload (2026-10-25)"): Z-Anime Base 1.73 / 1.68 / 1.60 s/it, FLUX.2
  klein base 4B 1.11 / 1.01 / 0.93, NewBie 1.13 / 1.06 / 0.98, NetaYume
  0.83 / 0.78 / 0.73. `loading.quantization_config` builds
  `Float8WeightOnlyConfig` / `Int8WeightOnlyConfig`, which dequantize each
  weight before every matmul; eager mode never fuses that away. The
  quantization buys memory, and pays for it in time.
- The default checkpoint, FLUX.1 Krea [dev], has so far rendered on this
  machine only at bf16 under sequential offload: 109.7 s for 28 steps
  (2.81 s/it). Its fp8 load waits on `GEN#22`'s card run.
- The undistilled checkpoints take minutes an image: Krea 2 Raw 329.8 s
  (52 steps, bf16 sequential), FLUX.2 klein base 9B 212.6 s (50 steps).

diffusers 0.40.0, the pinned version, ships each tool this needs
(checked in the 0.40.0 wheel): `ModelMixin.compile_repeated_blocks`,
`ModelMixin.set_attention_backend` (`native`, `_native_cudnn`, `flash`,
`sage` and their variants in `models/attention_dispatch.py`), and
`CacheMixin.enable_cache` with First Block Cache, TaylorSeer, MagCache,
FasterCache and Pyramid Attention Broadcast under `hooks/`.

Every speed change below that alters pixels is a reproduction question
first. The rule that a seed re-renders the same image
(`docs/rules.md`, Reproduction) holds across processes today; a choice that
changes the numbers must be recorded where `applied()`, the chunk and the
run id can see it, or be shown not to change them.

### R1. Compile the denoiser's repeated blocks

`transformer.compile_repeated_blocks(fullgraph=True)` (regional
compilation: one compiled block reused by every layer) after the load,
under model offload, so torchao's dequantize fuses into the matmul. The
plan has to answer:

- Windows: `torch.compile`'s Inductor needs Triton, which PyTorch ships
  for Linux only; the community `triton-windows` wheel is the usual route.
  Whether one exists for torch 2.13 on sm_120 is the first check. WSL
  (`wsl/`) already has Triton (`docs/design-notes.md`'s note on the C
  compiler for Triton's helper).
- Recompiles: each new size (and batch) can recompile; measure the first
  image at a size against the second, decide `dynamic=True` or marking the
  sequence dimension dynamic, and where Inductor's cache lives
  (`TORCHINDUCTOR_CACHE_DIR` beside the gallery, so a restart does not pay
  it again).
- What it composes with: model offload yes; sequential offload and
  Nunchaku's transformer are out of scope; a LoRA hot-swap
  (`loras.py`, `generate()`) recompiles unless diffusers'
  `enable_lora_hotswap` is set before the first adapter; Refine,
  inpaint and outpaint run sibling classes over the same transformer.
- Reproduction: whether a compiled render is pixel-identical to an eager
  one at the same seed on the card; if not, compile is a recorded choice,
  not a silent one.
- Where it is chosen: a loader option beside quantization and offload
  (`loader_choices.py`, the Models panel), off by default until the card
  says otherwise.

L, plus card. `PERF#1`.

**Next slice (CPU, plan only).** Write `docs/plan-regional-compilation.md`
for one initial family under model offload. Inspect the installed source
for repeated-block support and loader/sibling/LoRA lifecycle; record a

sites, and bounded implementation stages with fake-based checks. The plan
must separate first-image compilation, repeat-image timing, size changes,
pixels, system-RAM/commit and card peaks in its proposed measurement table.
List Windows/WSL dependency questions explicitly; verify current wheel
claims from primary sources when planning, without installing anything.
This slice ends with the plan and unresolved decisions, not a model load.
Keep the row OPEN for implementation, then CARD for its remaining run.

**Plan delivered, 2026-10-26:** [regional compilation](plan-regional-compilation.md)
records the installed API, candidate Windows wheel, narrow opt-in matrix,

### R2. fp8 with fp8 activations

The RTX 5080 (sm_120) has fp8 tensor cores; weight-only fp8 never uses
them. torchao's `Float8DynamicActivationFloat8WeightConfig` quantizes the
activations too and runs real fp8 matmuls, typically only fast under
compile (R1). It is a new quantization choice with its own name, since its
pixels differ from `fp8`'s, built through the same
`PipelineQuantizationConfig(quant_mapping=...)` rule; text encoders may
stay weight-only. The plan measures quality against bf16 at shared seeds
(the comparison tools already do this), the speed, and the load's RAM
(`GEN#22`'s peak applies to it too). M, plus card; waits on R1.
`PERF#2`.

### R3. Attention backend

`set_attention_backend` on the denoiser: `_native_cudnn` (no new
dependency), `flash` (FlashAttention 2 wheels) or `sage` (SageAttention,
which quantizes Q and K to int8 and so changes pixels). The plan checks
which have wheels for Windows on torch 2.13 and sm_120, measures each per
family (the DiTs' sequences are long, so attention is a larger share than
on SDXL's UNet), and records a pixel-changing backend as R1 records
compile. Under sequential offload the choice still applies. M, plus card.
`PERF#3`.

### R4. Step caching for the long, undistilled schedules

First Block Cache, TaylorSeer and MagCache skip or extrapolate a block's
work on steps where its output barely changes; reported gains are around
1.5-2x at some quality cost, largest on 30-50 step schedules and pointless
on the 4-8 step distilled checkpoints. An opt-in per render, so it is a
reproduction field: it widens the key once (`grid.CellKey`'s next
extension, existing run ids unchanged, the way `mask` was added) and rides
in the chunk. The plan picks one cache to start with, its threshold per
family from the authors' or diffusers' recommendations (never invented),
how it reaches the panel (likely one checkbox beside Steps for the
profiles that allow it), and measures quality at shared seeds on Krea 2
Raw, klein base and Z-Anime Base. L, plus card. `PERF#4`.

**Next slice (CPU, plan only).** Write `docs/plan-step-caching.md` for one
cache and one undistilled family, using author/library sources for its
parameters. Define opt-in fields and every reproduction carry site, old-key
compatibility, and hook reset between images/jobs, after cancellation and
when sibling pipelines share components. End with bounded implementation
stages, CPU checks and a finite shared-seed quality/time/RAM/card protocol.
No speedup is established until that protocol is run on the card.

**Plan delivered, 2026-10-26:** [step caching](plan-step-caching.md)
uses a sourced FBC default on one supported undistilled family, specifies
per-call hook cleanup and a finite comparison protocol, and coordinates
the speed recipes' single optional key extension. No cache was enabled;
`PERF#4` stays open.

### R6. Check `web/`'s shared global scope without a browser

`index.html` loads classic scripts that share one global scope (52 at the
2026-10-26 audit); only `app.js` runs anything. A duplicate top-level
`let`, `const` or `class`
across two files is a load-time `SyntaxError` that stops every later
script, and today only a smoke in a browser finds it. Every file but
`app.js` only declares at the top level (three read `document` while
declaring: `state.js`, `job-progress.js`, `runs.js`), so a Node script can
load them in `index.html`'s order into one `vm` context with a stub
`document` and fail on the first redeclaration or syntax error. Run from a
pytest so CI has it (Node is on the runner). S. `DEV#5`.

**Execution owner, 2026-10-26:** [Shared-scope guard](plan-tooling.md#shared-classic-script-scope).
The original execution sketch above needs one correction: `app.js` owns
top-level declarations too. Include it in syntax and cross-file collision
coverage without running its boot; a guard that excludes it is incomplete.
Derive the script list from HTML rather than freezing this snapshot's count.

## Gallery

### R8. Automatic whole-gallery backup

Backing up the whole gallery and password-protecting a bundle are both
Often (J9, J11 in `docs/design/preferences.md`); today every backup is a
press in the Bundles dialog. An automatic one - at start-up when the newest
backup is older than a set age, keeping the last N - runs through the
existing verified export (`bundles.py`) under the maintenance reservation
(`api_bundles.py`). The plan answers the password: an automatic bundle
cannot ask for one, so either it is unencrypted (said plainly), or the
password is kept by the OS (Windows Credential Manager through `keyring`),
or automatic backups are off whenever Matt wants a password. Also where the
age and count live (the saved settings) and what the page says while one
runs. M to L. `GAL#6`.

**Next slice (CPU, plan only).** Write `docs/plan-automatic-backups.md`
with default-off activation, an explicit unattended-password decision and
managed retention rules. Reuse the existing maintenance reservation and
verified `keep_gallery=True` export; count age/success only after read-back
verification. Retention must distinguish automation-owned archives from
manual bundles and preserve prior good copies on failure; a bundle may be
the only surviving gallery copy. Define startup/preload admission, shutdown,
disk-space checks, status/errors and scratch-gallery test cases. Never
store a password in saved JSON, URLs or logs, or silently fall back to
plaintext when credentials are absent. End with implementation stages and
the policy decisions Matt must settle before enabling automation. This
slice does not turn on backups, prune archives or run a live export.

**Plan delivered, 2026-10-26:** [automatic backups](plan-automatic-backups.md)
specifies verified publication, startup admission, ownership/retention,
failure recovery and unattended-password options. Nothing was exported,
pruned or enabled; `GAL#6` remains open for implementation and its explicit
activation policies.

## Edits - Matt's call

### R9. Edit an image by instruction

Refine is Often (H1-H5); every edit today is a denoise pass from the
source, a painted mask or a padded canvas. Instruction-editing checkpoints
take the source image and a sentence ("make it night"): FLUX.1 Kontext
[dev] (`FluxKontextPipeline`, about 12B, the FLUX.1 load class and its
licence) and Qwen-Image-Edit (the Qwen-Image size, so in practice under
Nunchaku on WSL, as Qwen-Image is). A hand-entered Kontext id loads today
through the catch-all `flux` profile and runs text-to-image only; its
inpaint is refused (`DiffusersBackend._inpaint_supported`). FLUX.2 [klein]
already conditions on gallery references, but Matt doesn't run klein and
rates references Never (I3). Built, it would be a new pass kind beside
refine and inpaint: the source a gallery id, the instruction and kind in
the chunk and the key. XL, plus card. Worth a plan only if Matt wants
editing by sentence. `INP#11`.

### R10. A face and hand detailer

The 2026-10-24 review put this off until Generate then refine was built,
since a batch form would share its in-job second pass; that pass is built
(`docs/plan-then-refine.md`, phases 1 and 2). A detailer finds faces or
hands, builds a mask per box and runs the existing inpaint over each,
composited as every inpaint is. The decision is the detector: the usual
anime face and hand models are YOLO weights trained with Ultralytics,
which is AGPL-3.0 against this repository's Apache-2.0, so the plan needs
a detector whose code and weights may be used here (MediaPipe's face
detector is Apache-2.0; anime faces need checking), downloaded on first
use like the critic's model. Inpaint is Sometimes (H7). L, plus card.
`INP#12`.
