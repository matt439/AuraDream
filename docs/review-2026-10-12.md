### Gallery actions

#### R1. If the remembered More seeds count times the picked batches is over max_grid_images, the dialog never opens, so the count cannot be lowered

**medium** · Gallery actions · confirmed · effort S · `p4-gallery-dialogs`

**Where.** web/more-seeds.js:131-166 (openMoreSeeds asks before showModal, using the remembered MORE_SEEDS_KEY count); backend/api_more_seeds.py:57-65 (422 for the whole request)

**Observed.** The dialog opens only after the first preview answers, and that preview uses the last count queued. If batches × count is over 1024, the server answers 422 "2 batches × 600 is 1200 images; a press may queue 1024. Ask for fewer, or pick fewer batches." That text goes to the gallery line and the dialog stays closed. Pressing More seeds… again gives the same result. The count box that would let you 'ask for fewer' is inside the dialog that cannot open. The remembered count only changes after a successful queue, so the user can either pick fewer batches or clear site storage. A realistic case: queue 64 more of one big batch, then later pick 17 batches (17 × 64 = 1088).

**Repro.** Fake server (FLUX.1-Krea-dev, fresh --data) holding images from at least two runs. In the page: remember(MORE_SEEDS_KEY,'600'), turn Select on, pick one card from each of two runs, press More seeds…

**Evidence.** Browser log: 'open=false | gallery line=2 batches × 600 is 1200 images; a press may queue 1024. Ask for fewer, or pick fewer batches.' A second press also gave 'second press open=false'. Screenshot b10.png shows the message in the gallery line and no dialog.

**Also seen.** The scale follow-up (gap-other-families-and-scale-2, folded in here) hit the same refusal with nothing picked: search `fox` (320 single-image batches) at the default count 4 gave '320 batches × 4 is 1280 images; a press may queue 1024…', and 1,024 picks gave '1015 batches × 4 is 4060 images…'. At the default count any scope over 256 batches is blocked.

**Recommendation.** In openMoreSeeds, if the opening preview fails with the over-cap 422 (the message matches /^\d+ batch/), open the dialog anyway: put the refusal in #more-seeds-error and set aria-invalid on the count box. moreSeedsHold and runMoreSeeds already handle that hold. A simpler fix is to retry the opening preview once at count 1 (or at floor(1024/batches), taking the batch count from the refusal text) and say why the count was lowered.

**Fixed** (`left/p4-gallery-dialogs`). Before, if the opening check came back with the 422 refusal by count ("N batches × C is…"), the dialog did not open. Now openMoreSeeds opens it anyway with nothing listed: the refusal shows in the count line and #more-seeds-error, the count box is aria-invalid and Queue is held with that reason. A count that fits then lists the batches. Covered by a new smoke-more-seeds step (0c21cc3). Since then, a second More seeds press while the first is still waiting on its check does nothing (msWaiting). Before, two such presses aborted each other's check in a loop that never yielded and froze the tab. Covered by a new smoke-more-seeds step: two presses in one tick queue once and close the dialog (11979ff).

#### R2. A Swap tags press made before the 400 ms check finishes is dropped: "Checking the swaps…" flashes and disappears

**medium** · Gallery actions · confirmed · effort S · `p4-gallery-dialogs`

**Where.** web/tag-swap.js:390-394 (queueSwap returns on any hold) and 376-388 (syncSwapQueue clears the press's message once the check lands)

**Observed.** Mass refine and More seeds wait for the check of what the dialog shows before acting on a press (runMoreSeeds/runRefineBatch loop on the check). Swap tags does not. queueSwap writes 'Checking the swaps…' into #swap-error and returns, and when the check lands a moment later syncSwapQueue erases that message. So typing Find and Replace and pressing Enter or Ctrl+Enter straight away queues nothing, leaves no message, and the dialog stays open with Queue live. The user has to notice and press again. Doing the same in More seeds (edit, then Enter) queues and closes the dialog.

**Repro.** Pick one card that has 'smile' in its prompt. Open Swap tags…, type 'smile' in Find, Tab, type 'grin', then press Enter at once.

**Evidence.** A MutationObserver on #swap-error recorded ["Checking the swaps…",""]. 1.5 s later: open=true, Queue read 'Queue 1 image', and no new image was in the gallery. The same sequence in More seeds (type 3, Enter) gave open=false and the job was queued.

**Recommendation.** Give queueSwap runMoreSeeds' loop: while swapAsking is set or JSON.stringify(swapPayload()) !== swapAnswerKey (and the payload has swaps), clearTimeout the timer and await the swap check, then bail if the dialog closed. After that, read swapHold() and either say the hold or queue. That needs the check function to return a promise, as runMoreSeedsCheck does.

**Fixed** (`left/p4-gallery-dialogs`). queueSwap now waits for the check of what the rows say before acting, as runMoreSeeds and runRefineBatch do, so Enter typed right after Find/Replace queues and closes the dialog (0c21cc3). The reviewer found that two presses during one check froze the tab, because each aborted the other's request in an endless microtask loop. Now only one press waits (swapWaiting); runMoreSeeds and runRefineBatch, which had the same bug already, got msWaiting and rbWaiting. Each of the three smokes has a step where two presses in one tick queue exactly once (11979ff).

#### R3. Opening the recycle bin silently throws away the whole gallery selection, up to 1024 picks

**low** · Gallery actions · adjusted · effort S · `p4-gallery-dialogs`

**Where.** web/bin.js:128-147 (enterBin/leaveBin call clearSelection)

**Observed.** enterBin() and leaveBin() both call clearSelection(). With 6 cards picked, pressing Bin and then Bin again leaves 0 selected. Nothing is shown in #gallery-error, the Bin title gives no warning, and there is no undo. Elsewhere the selection is designed to survive searches, filters, sheets and leaving select mode ('turning a mode off is no request to throw away forty picks'). A quick look into the bin for a keeper to restore costs the whole selection.

**Repro.** Turn Select on, pick several cards, press Bin, then press Bin again.

**Evidence.** Browser log: 'before: 6 selected' → 'in bin: Click cards to pick them | error line=' → 'back: … sel=0'.

**Verified.** Reproduced: 1 pick, Bin pressed twice, 0 picks and #gallery-error empty. The clearing is deliberate and documented in rules.md:3715 ('enterBin() sets binMode, clears the selection') and in the comment at bin.js:125 ('the selection is the gallery's, and goes'). The bin needs its own picks for Restore picked, so it cannot simply reuse the gallery's selection. No reason is written down for dropping the gallery selection rather than stashing it, though, and it goes against the selection note that 'turning a mode off is no request to throw away forty picks' (design-notes, 'The gallery selection'). Adjusted to a documented-but-unjustified UX loss, not a bug.

**Recommendation.** In enterBin, stash the selection Map and selectAnchor, then clear. In leaveBin, restore the stash and drop any ids binned or deleted since through forgetSelected. Restored ids are live again and can stay. Add a line to rules.md and design-notes saying the gallery's picks survive a look into the bin.

**Fixed** (`left/p4-gallery-dialogs`). enterBin sets the gallery's picks and anchor aside (stashSelection) and leaveBin puts them back (unstashSelection), dropping the bin's own picks; forgetSelected also drops binned or deleted ids from the set-aside picks (0c21cc3). leaveBin now also drops any set-aside pick that the bin's view listed (records with binned_at) before the gallery's records replace it. That covers a pick another tab binned without this page hearing of it. The smoke-bin step now covers that case, and its two Bin presses use els.bin.click(): a coordinate click was lost in about 1 run of 3 when the page's scroll moved under it (11979ff).

### Storage, bin and bundles

#### R5. A stale *.png.part or *.webp.part in the images folder blocks every bundle export, import and even the counts, permanently. Nothing in the app sweeps it or explains how to fix it.

**medium** · Storage, bin and bundles · confirmed · effort S · `p1-storage-safety`

**Where.** backend/bundles.py:93-94 (_inventory), backend/storage.py:688-691 (discard_bundle_leftovers), backend/main.py:233

**Observed.** _inventory() refuses on any name ending in .part. preview(), export_bundle() and import_bundle() all call it. The only cleanup at startup and before each bundle operation is discard_bundle_leftovers. It filters _stale_partials() down to _bundle_leftovers() (bundles/*.part, .bundle-* work folders, staging), so image partials are never removed, however old. Only clear_history sweeps them, and that is the CLI that deletes the gallery. The dialog shows 'The gallery counts could not be read.', Bundle & clear is held with 'Refresh the gallery counts first', and the status line says 'finish or recover the incomplete image write first: 20261001-000000-5-abc.png.part'. It gives no folder and no action, and nothing in the UI can 'recover' anything. A power cut or a killed process during image.save leaves exactly this file (storage.py:524-581).

**Repro.**

1. Start fake_server --port 7915 --data <scratch>/data-1 and generate a few images.
2. Create outputs/20261001-000000-5-abc.png.part with an mtime a week old.
3. GET /api/gallery/bundles/preview.
4. POST /api/gallery/bundles/import with a saved bundle.
5. Restart the server and repeat step 3.

**Evidence.** preview returns 400 {"detail":"finish or recover the incomplete image write first: 20261001-000000-5-abc.png.part"}. The import status is state=failed with the same error. After a restart the file is still there and preview still refuses. Screenshot: scratchpad/storage-bin-bundles/b1-bundles-part.png.

**Recommendation.** Under the reservation the bundle operation already holds, sweep image and thumbnail partials older than PARTIAL_SETTLE_SECONDS at startup and before each bundle operation. A stale <name>.png.part whose final name a row already names, with the .png missing, is the only copy of a committed image (the rename failed after commit, see storage.py:576-581). Rename that one into place, never discard it. clear_history's sweep has the same blind spot and should get the same treatment. Keep _inventory's refusal for fresh partials only, and make the message name the folder and the action: 'outputs\X.png.part is an unfinished image write; if no render is running, delete it'.

**Fixed** (`left/p1-storage-safety`). `storage.settle_partials` replaces `discard_bundle_leftovers` and runs at startup, at every bundle preview, and before export and import. It renames a stale `<name>.png.part` into place when its row exists and its PNG does not, and it discards every other stale partial, thumbnail `.webp.part` files included: `thumbnail_for` can be killed mid-encode, and nothing re-encodes a thumbnail once it is in place, so the card falls back to the PNG. `clear_history` settles the same way before its thumbnail sweep. `summarise` counts recoverable images, one per interrupted save. A `.part` that remains is refused with its name, its folder and what to do. (9cc6e4c, 9fe9a63)

**low** · Storage, bin and bundles · confirmed · effort S · `p1-storage-safety`

#### R9. `lora:none` does a substring match on 'none' instead of finding images made without a LoRA, despite search.py's own comment

**low** · Storage, bin and bundles · adjusted · effort S · `p7-search-bundle-text`

**Where.** backend/search.py:36-37 (comment), 108-117 (str branch returns before NULL_TOKENS)

**Observed.** The FILTERS comment says '`lora:none` is everything rendered without one'. For text keys, filter_clause returns the LIKE clause before NULL_TOKENS is checked. So lora:none means LIKE '%none%' and finds nothing, and the images made without a LoRA cannot be found by search. The same applies to quant:none for unquantised rows. lightbox-cfg.js:108 even says 'there is no term for "no adapter"', which contradicts the backend comment.

**Repro.** In a gallery with no LoRA images, search lora:none, then quant:none, and compare with refine:none.

**Evidence.** lora:none returned 0. quant:none returned 0, although rows with quantization None exist. refine:none returned 9 of 9.

**Verified.** Real for lora, refuted for quant. Code trace: search.filter_clause returns the LIKE branch for str keys (search.py:108-117) before NULL_TOKENS is checked, so lora:none means LIKE '%none%'. On port 8015, lora:none returned total 0 while every row has lora null, contradicting search.py:36's comment. The quant:none part is wrong: an unquantised load stores the literal mode string 'none' (loader_choices.py:16, config QUANT_MODES), so quant:none's substring match does find BF16 renders. My fake's rows are fp8, which is why that search returned 0. NULL quantization occurs only on legacy or imported rows. model_id is never NULL. lightbox-cfg.js:108 already says there is no term for 'no adapter', so the bug is the comment versus the behaviour, and lora is the only key affected.

**Refuted part.** `quant:none` works: an unquantised load stores the literal mode `none`, so its substring match finds BF16 renders. Only `lora` is affected.

**Recommendation.** In filter_clause, treat an exact none/null/off on lora as 'lora IS NULL' (lora:=none stays the literal name). Leave quant alone, since 'none' is a real stored value there. Then build lora:none into lightbox-cfg's terms and the search tip. If this is not wanted, correct the comment at search.py:36 instead.

**Fixed** (`left/p7-search-bundle-text`). filter_clause now reads an exact none/null/off on lora as `lora IS NULL`, and `lora:=none` stays the literal name. quant is left alone, because 'none' is a stored mode there, and a test pins quant:none to the substring match. For an image made without an adapter, lightbox-cfg's ladderQuery now adds `lora:none`. smoke-compare-cfg checks that query and the 3 options it finds. The search.py docstring, rules.md and design-notes are updated. c0438d3.
