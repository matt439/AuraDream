# Refine pass — Review Report

## Verdict

The pass itself holds up. The core and lifecycle reviewers checked every
sibling's call against diffusers 0.40 (signatures, the defaults the app does not
pass, `get_timesteps` and `begin_index`, `forced_mu` and the shifted sigmas
reaching a shared scheduler, true CFG and the negative prompt, preprocessing,
the per-image generator, `num_timesteps` after slicing,
`maybe_free_model_hooks`, the offload hooks and `LOCAL_DIFFUSION_DEVICE`, both
unload paths letting the sibling go, LoRA, quantization, the preview callback)
and found nothing. The storage reviewer confirmed that run ids of grids without
a pass are unchanged and that `refine_key` formats the same at submit, on resume
and after a reindex. The CLI's `--scale` rounding is the page's to the bit.

The findings are at the edges. One medium: a prompt comparison carries the
grid's new strength axis and silently multiplies its image count (F1, one line).
The rest are low:

- The grid validator checks a base steps/strength pair that the axes replace,
  and on a checkpoint with no pass it answers with the wrong reason (F2, F3,
  F16).
- Advisories and estimates read strength as a number where the pipeline uses an
  integer start index: the duplicate count, the step cost, and a progress test
  that cannot tell the two apart (F4, F11, F15). One step-count test only checks
  what the fake computes itself (F14).
- For checkpoints outside the catalogue, the profile's guess before a load
  disagrees with the live class in both directions: a request accepted then
  rendered without its pass, a stale Strength box, and a page that drops the
  source (F5, F6, P1).
- Page notes about the source: a deleted source is dropped silently or not at
  all, contrary to CLAUDE.md; a note quotes 0.4 for an empty box; Reuse's
  warning forgets the Strength box (F7, F8, F9).
- A PNG-only reindex keeps the refine id verbatim, as it already did for
  references (F10).
- A CLI guard that lets NaN through (F12), and doc text that labels arithmetic
  as measurement, overstates what is held on the card, or blames diffusers for
  Anima (F13, F17-F23).

### MEDIUM

#### F1. `web/analysis.js:983` — A prompt comparison keeps the grid's strength axis and multiplies its image count

`comparePayload()` spreads `gridPayload()` and then blanks every grid axis, so
that "the versions are the one thing that varies, crossed with the seeds" (its
own comment; CLAUDE.md holds a comparison to "versions times Seeds" images). The
commit added `strength_axis` to `gridPayload()` (web/generation.js:258) but not
to the blanked list at web/analysis.js:977-984, and did not touch analysis.js.

The grid's Strength box is live whenever a refine source is set
(`syncConditioning`, web/sizes.js:212-216), whether or not the grid section is
open, and it is persisted with the panel (`PANEL_FIELDS`). A sweep left in a
folded grid section, even from an earlier session, is therefore enough. The
server accepts it: `grid._sampling_values` keeps the axis whenever `refine` is
set, and `expand` multiplies by it.

**Failure.** FLUX.1 Krea dev, a refine source picked, the grid's Strength axis
holding `0.2,0.4,0.6` with the grid section folded. Check a prompt, write Your
version, Seeds 4, Batch 1. The preview reads "24 images · 2 variants × 4 seeds ·
batch 1", and Run comparison queues 24 refine passes instead of 8. The sheet
varies variant, strength and seed; `chooseAxes` puts seeds in columns and
variants in rows and pins strength, so the opened sheet shows a third of what
was rendered.

**Fix.** Add `strength_axis: ''` beside `lora_scale_axis: ''` in
`comparePayload()`. Whether a comparison should carry the panel's refine source
at all is a separate question; it does today, as it carries the LoRA. If it
should, the comparison preview ought to say the versions are refine passes of
image N.

**Evidence.** Two independent reproductions: /api/grid/preview with
comparePayload's shape on a fake server (8 cells with the axis empty, 24 with
`0.1,0.2,0.3`), and the page itself in headless Edge
(`comparePayload(comparedVariants())` carried the axis with the section folded;
the preview text as above). Re-run by hand after the workflow on a fresh fake
server: 8 cells, then 24.

*ui-state*; also `web/analysis.js:973`, `web/generation.js:258`,
`web/sizes.js:212`, `backend/grid.py:403`. Merged from 2 verified candidates.

### LOW

#### F2. `backend/schemas.py:126` — A refine grid is refused over the base steps/strength pair that an axis replaces in every cell

`_refine_leaves_a_step` is a model validator on `GenerateRequest`, so it also
runs on the `GridRequest` body and on the CLI's base request (generate.py:518)
before the axes apply. When a strength or steps axis is set, the base values are
only fallbacks that `grid.expand` replaces in every cell, and `expand` already
checks each cell by name. That per-cell check is the contract the design notes
and the validator's own comment state ("for a grid is every cell ... refused
here, by name, when the grid is built"). An absent strength is filled in from
the profile before the check (0.1 on FLUX.1), so the refusal can name a value
the user never typed.

**Failure.** FLUX.1 Krea dev, Steps 8, Strength box untouched, a refine source,
Strength axis `0.3,0.5` (cells at 2.4 and 4 steps). /api/grid and
/api/grid/preview answer 422 "strength 0.1 of 8 steps is less than one step";
`generate "a fox" --refine 1 --steps 8 --grid-strength 0.3,0.5 --dry-run` exits
2 with the same message. Steps 4 with a steps axis `20,28` is refused the same
way. The workaround is to raise the unused base value.

**Fix.** Skip the base check on a `GridRequest` whose `strength_axis` or
`steps_axis` is set (the cells are checked in `expand`), and build the CLI's
base request the same way. Alternatively, move the check out of the schema into
the per-cell build altogether, which also settles F3.

**Evidence.** `GridRequest` construction, TestClient on /api/grid/preview and
the CLI dry run all refuse; with a base strength of 0.3 the same grids expand
into valid cells. Re-run by hand after the workflow: refused for Steps 8 with
the axis `0.3,0.5`, with and without an explicit 0.1, and for Steps 4 with a
steps axis `20,28`; accepted with a base strength of 0.5.

*correctness*; also `backend/generate.py:518`, `web/generation.js:258`. Merged
from 3 verified candidates.

#### F4. `backend/grid.py:500` — The duplicate count misses strengths that start the schedule at the same step

Every sibling uses strength only to pick an integer start index (the flow
pipelines `t_start = int(n - n*s)`, SDXL `n - int(n*s)`), so two strengths with
the same index render byte-identical images under one seed. `cell_key` keys on
the strength as typed (`refine_key` "id@0.6" against "id@0.7"), so
`duplicate_count`, documented as comparing cells "as the pipeline will *run*
them", reports none, and the preview's "would be identical" and the CLI's
dry-run warning stay silent. Low-strength FLUX.1 sweeps, which the design notes
recommend, and the few-step checkpoints hit it most. The run itself is correct:
duplicates render by design, and the hash-based distinct count reports them
afterwards.

**Failure.** FLUX.1 Krea dev at 28 steps, axis `0.05-0.15x0.01`: 11 cells, 4
distinct start indices, 0 duplicates reported. schnell (4 steps), `0.5-0.9x0.1`:
2 duplicates, 0 reported. Z-Image Turbo (8 steps), `0.2-0.5x0.05`: 4 duplicates,
0 reported. The sheet labels identical images as different strengths.

**Fix.** In `duplicate_count` only, compare refine cells by the start index the
sibling will compute (the flow or the SDXL rounding, by the checkpoint's family)
rather than the raw strength. Keep `CellKey` and `run_id` on the raw strength.

**Evidence.** Probe scripts printing each strength's `t_start` beside
`duplicate_count`'s 0 for each case.

*preview-advisory*; also `backend/grid.py:505`, `backend/grid.py:122`. Merged
from 2 verified candidates.

#### F10. `backend/storage.py:892` — A PNG-only reindex keeps the chunk's refine id verbatim, so it can name an unrelated image or the image itself

`index_file` stores the chunk's `refine` id unchanged, and `--from` copies it
unchanged into the new PNG. A gallery id belongs to the database that wrote the
file. After `reindex --from <other gallery>` without `--database` (the README's
WSL-into-Windows merge), or an in-place rebuild after the database is lost
(AUTOINCREMENT ids renumber after deletions), the id can point at another
picture. The refusals only check that the id exists, so Re-render, Reuse and
`--from-image` refine the wrong image and record it as the reproduction. The
database merge avoids exactly this by remapping. Reference ids already behaved
this way, and the commit mirrors that on purpose (test_refine.py:375-378), so
this extends an inherited flaw to the new field.

**Failure.** WSL gallery: source id 1, refine id 2. The Windows gallery already
holds "a blue whale" at id 1. After `reindex --from <wsl outputs>`, the copied
refine row has refine=1: the whale. In place: delete 1, refine 2 into 3, lose
the database, reindex. The refined row, now id 2, has refine=2, itself.

**Fix.** On a PNG-only reindex, resolve the source by content hash where the
chunk carries the source's (add it to the chunk from now on); otherwise store
None and count it unresolved, as the merge does. Do the same for reference ids.

**Evidence.** Two scratch galleries reproducing both cases.

*data-integrity*; also `backend/reindex.py:395`, `backend/main.py:1106`,

#### F11. `backend/storage.py:519` — Refine rows skew the per-step cost that prices direct renders at the same size, and the other way round

`step_cost_ms` puts refine and direct rows of one size into one median, after
dividing a refine row by `steps_run`. A pass's per-image fixed costs (resize,
text encode, VAE encode and decode) dominate at its few steps. On the flow
pipelines the floor also counts one step fewer than diffusers runs at FLUX.1's
default (28 steps at 0.1: 2 counted, 3 run). The floor is the documented choice
and accounts for about 1.5x of the error; the fixed costs account for the rest.
Once refine rows dominate a size, direct estimates there run about 2.3x high,
and refine cells priced from direct rows run about 2.3x low.

**Failure.** FLUX.1 Krea dev at 1536², a gallery of default refines (16.9 s
each): 8450 ms per step against 3618 measured direct, so a direct 28-step cell
is estimated at 237 s against 101 s. A 0.1 refine priced from direct rows: 7.2 s
against 16.9 s.

**Fix.** Keep refine rows out of the direct median and price refine cells from
refine rows, or model a per-image constant beside the per-step cost.

**Evidence.** A scratch database with three refine rows; `step_cost_ms` and
`estimate_seconds` printed as above, against verified.md's measured times.

*estimate*; also `backend/grid.py`, `backend/refine.py:142`.

#### F13. `backend/backends/diffusers_backend.py:725` — Under model offload the VAE stays on the card through a pass's whole denoise, though the docs say nothing more is held

Each refine call first encodes the source with the shared, hooked VAE. The VAE
is last in the offload chain, so nothing moves it off the card until `_refine`'s
final `maybe_free_model_hooks()`. It sits beside the denoiser for every step,
which a text-to-image call never does. The commit's own measurements show refine
peaks about 0.16 GiB higher (verified.md:316, 318). The README, the design notes
and the commit message say nothing more is held on the card, which is true of
the weights but not of the peak. This is stock diffusers behaviour and costs
little.

**Failure.** FLUX.1 Krea dev, fp8, offload=model, a 1 MP image refined at 1.5x:
the transformer and the VAE are both resident for every step of the pass, at a
size where verified.md says the card is already within a gigabyte of its top.

**Fix.** Say so in the docs (a pass peaks about the VAE's size above a direct
render), or offload the VAE after the encode under offload=model.

**Evidence.** A tiny FluxPipeline built for the probe and placed by
`loading.place_pipeline` under offload=model: the VAE on the CPU during a
text-to-image denoise, on cuda:0 throughout the refine denoise.

*docs-drift*; also `README.md:600`, `docs/design-notes.md:398`,
`docs/verified.md:316`.
