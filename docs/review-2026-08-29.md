# Code review — 2026-08-29

Multi-agent review of the whole repo at commit `da7f774`. No code was changed;
this is a record of findings only.

**Method.** 16 finders, each scoped to one dimension and one set of files, ran
blind to each other over the full source. Their 59 raw findings were merged and
de-duplicated to 47 (12 dropped as wrong, intended, or pure style). The top 12
by severity then went to two independent verifiers each: one instructed to
*refute* the finding and default to refuted when uncertain, one instructed to
*trace the call path* from an entry point to the defective line and refute if no
such path exists. Only findings both verifiers failed to kill are marked
CONFIRMED. Three completeness critics then hunted what the finders missed —
untouched code, cross-file invariants, and real operational failure modes — and
their findings went through the same two-lens gate. 51 agents total.

**Reading the results.** CONFIRMED findings survived adversarial verification and
carry a concrete failure scenario. DISPUTED means the two verifiers split, and
the split itself is reported. The unverified section fell outside the
verification cap and is leads, not conclusions — it has not been checked and
some of it will be wrong.

Every finder read `CLAUDE.md` first and was told that code matching a documented
decision is not a finding unless the documented reasoning is itself wrong. Two
of the confirmed findings are exactly that case, and both name the CLAUDE.md
line that needs correcting alongside the code fix.

# Krea Local — Review Report

## Verdict

The code is well-reasoned and unusually well-documented, and that is precisely where it fails: the two most damaging bugs both live inside constraints that CLAUDE.md asserts as settled fact. `_shifted_sigmas` pre-shifts a schedule the pipeline then shifts again (the documented rationale, "`__call__` accepts `sigmas`, not `mu`", is true of the signature and wrong about the behaviour), so every Krea-2-Turbo image ever produced ran on a shift of ~2.30 instead of 1.15. The dominant class of problem is **invariant drift between a documented decision and the code that is supposed to enforce it** — a single-load rule the backend quietly bypasses, a "source of truth" profile table duplicated verbatim into `schemas.py` and `index.html` and left behind by the FLUX default switch, a reproducibility guarantee broken by JSON number precision, a favorites filter that vanishes in a fallback query. Secondary theme: nothing coordinates the three concurrency actors (event loop, gen worker, `clear.py`'s separate process), which produces the unload/reload, orphan-PNG and re-entrant-pager races.

Fix the sampling schedule and the seed round-trip first — everything else is recoverable, but those two silently corrupt output and destroy reproducibility of every image already on disk.

## Confirmed findings

### HIGH

#### `backend/backends/diffusers_backend.py:266` — mu shift is applied twice

`_shifted_sigmas()` computes `sigma' = e^mu / (e^mu + (1/sigma - 1))` and passes the result as `sigmas`. `Krea2Pipeline` does not treat `sigmas` as a final schedule: it computes its own mu (1.15, hard-coded for `is_distilled`) and forwards it to `set_timesteps`, where `FlowMatchEulerDiscreteScheduler` applies `_time_shift_exponential` — byte-for-byte the backend's formula — because the cached `scheduler_config.json` has `use_dynamic_shifting: true`. The shift multiplies the odds `s/(1-s)` by `e^mu`, so the mus add: the effective shift is `mu_user + 1.15`.

**Failure:** Turbo at profile defaults (steps=8, mu=1.15) runs `[1.0, 0.986, 0.968, 0.943, 0.909, 0.857, 0.769, 0.588]` instead of the intended `[1.0, 0.957, 0.905, 0.840, 0.760, 0.655, 0.513, 0.311]` — seven of eight steps above sigma 0.58 and a final Euler jump of 0.588→0. Reuse reproduces the same wrong schedule, so nothing ever looks inconsistent. FLUX is hit only via an API client that omits `mu` and takes the schema default (see `schemas.py:15`); both first-party clients send `mu: null` there.

**Fix.** `_shifted_sigmas(steps, 1.15)` reproduces the pipeline's own default schedule exactly, so at the profile default the correct action is to pass nothing. Compensate for the shift the scheduler will apply:

```python
sched = getattr(pipe, "scheduler", None)
dyn = getattr(getattr(sched, "config", None), "use_dynamic_shifting", False)
if request.mu is not None and "sigmas" in self._call_params:
    if not dyn:
        kwargs["sigmas"] = self._shifted_sigmas(request.steps, request.mu)
    else:
        # The pipeline injects its own mu behind `sigmas`; shifts compose additively.
        pipe_mu = 1.15 if getattr(pipe.config, "is_distilled", False) \
                       else calculate_shift(image_seq_len, ...)
        delta = request.mu - pipe_mu
        if abs(delta) > 1e-9:                      # delta == 0 -> omit sigmas entirely
            kwargs["sigmas"] = self._shifted_sigmas(request.steps, delta)
```

Test the schedule the *scheduler* ends up with, not the one the backend computes. Correct the CLAUDE.md `sigmas`/`mu` bullet in the same change — its stated reasoning is why the bug exists.

#### `web/app.js:397` — 63-bit seeds lose precision in JS, so Reuse reproduces a different image

`jobs._generate` draws `random.randint(0, 2**63 - 1)` whenever `req.seed is None` — the default, since the box ships empty and the dice button clears it. `ImageRecord.seed` (`schemas.py:54`) serializes as a bare JSON number and ~99.9% of that range exceeds `Number.MAX_SAFE_INTEGER`, so `res.json()` rounds it. Every downstream consumer uses the rounded value: `reuse()` (397), `renderLightbox()` (419), `collect()` (193). Measured: 7283207964119141687 → 7283207964119141000.

**Failure:** `storage.save_image` writes the *true* seed into the filename and PNG metadata, so disk is right and only the UI is wrong — the failure is invisible. Reuse + Generate silently produces a different image while claiming the settings were reproduced, defeating commit 2922c44 and CLAUDE.md's per-image-seed guarantee. (The 422-on-round-up sub-case is real but ~1e-16 per draw; ignore it.)

**Fix.** Stop minting seeds JS cannot hold, but do **not** just lower `_MAX_SEED` — it is also the wrap modulus at `jobs.py:197` / `generate.py:296`, and lowering it makes a hand-entered `2**60` wrap to 0:

```python
_MAX_SEED = 2**63 - 1          # column bound + wrap modulus, unchanged
_RANDOM_SEED_MAX = 2**53 - 1   # Number.MAX_SAFE_INTEGER
...
base = req.seed if req.seed is not None else random.randint(0, _RANDOM_SEED_MAX)
```

Same in `generate.py:184`. Add a regression check that a 19-digit recorded seed survives Reuse exactly. This does not repair rows already in the DB; if those matter, serialize `ImageRecord.seed` as a string (`field_serializer`), accept `int | str` on `GenerateRequest.seed`, and treat it as opaque in `reuse()`/`renderLightbox()`/`collect()`.

### MEDIUM

#### `backend/main.py:116` — unload during a running job frees no VRAM and makes the worker reload mid-sweep

`unload_model()` and the shutdown hook call `backend.unload()` with no coordination against `jobs._gate`. `unload()` takes only `self._lock`, which `generate()` never holds, so `self._pipe` goes None mid-denoise — but the worker bound `pipe = self._pipe` at line 216, so the pipeline stays reachable, `gc.collect()` frees nothing, and `/api/status` reports "not loaded" with 13 GB resident. The next run of the sweep then hits `if self._pipe is None: self.load()` (212-213) and reloads on the gen thread while holding `_gate` — the second load path CLAUDE.md's single-`ensure_loaded()` rule forbids. `setBusy()` (app.js:199-207) leaves the Unload button live throughout.

**Failure:** 64-run sweep, click Unload. 200 OK, dot flips to "not loaded", nvidia-smi unchanged, then minutes of frozen progress bar while the worker reloads, then the sweep continues. Status self-corrects to "ready" afterwards (`main.py:92` re-derives it), which is backwards. Narrow extra window: `unload()` between the None check (212) and the re-read (216) gives `TypeError: 'NoneType' object is not callable`; between 216 and 268 it clears `_call_params`, stripping *every* kwarg including `prompt`. **Not** part of the bug: no duplicate `from_pretrained` — `load()` serializes on `self._lock` and the second caller no-ops.

**Fix.** Add `def busy(self): return self._gate.locked()` to `JobManager`; have `POST /api/model/unload` return 409 while a job is non-terminal. Replace the `if self._pipe is None: self.load()` fallback in `generate()` with a raise (the CLI already loads explicitly at `generate.py:261`). Disable `els.unload` in `setBusy()`. In `lifespan`, set `cancel_requested` on non-terminal jobs and `jobs._pool.shutdown(wait=True)` before unloading — this bites on a forced second Ctrl-C or with no SSE client attached, since uvicorn otherwise waits on the open stream.

#### `backend/schemas.py:15` — GenerateRequest hardcodes the Turbo profile while `settings.model_id` defaults to FLUX

`steps=8`, `guidance_scale=0.0`, `mu=1.15` are the `krea-2-turbo` row of `_PROFILES` copied into the schema. Commit d826124 pointed `settings.model_id` at `black-forest-labs/FLUX.1-Krea-dev` (28 / 3.5 / None) and never reconciled it. `index.html:44-46` is a third copy of the same three numbers.

**Failure:** `curl -d '{"prompt":"a lighthouse in fog"}'` — and FastAPI's own `/docs` "Try it out", which prefills from these defaults — runs FLUX at 8 steps, guidance-embedding 0.0, and a sigma schedule truncating at 0.311 instead of ~0.036, double-shifted (FLUX computes its own `calculate_shift` mu on top). The browser reaches the same numbers via `index.html`'s static values if Generate/Ctrl+Enter fires before the first `/api/status` lands — narrow, since `/api/status` answers without the model loaded, but reachable on a reload during an in-flight load. The CLI is clean; it resolves the profile itself.

**Fix.** Default the three to `None` and fill from `defaults_for(settings.model_id)` in a `@model_validator(mode="after")`; `model_defaults` imports nothing, so no cycle. **Gate mu on `model_fields_set`, not `is None`** — `app.js:192` sends `mu: null` deliberately to mean "no shift", and an `is None` fill-in would force 1.15 back onto a user who cleared the box and make that image un-reproducible from its own record. Update `index.html:44-46` to match, or better, seed them from `/api/status`.

#### `backend/storage.py:190` — LIKE fallback drops the favorites filter and miscounts total

`list_images` builds one `where`/`params` pair that correctly ANDs `favorite = 1` with the FTS predicate, then the `except sqlite3.OperationalError` branch hand-writes an independent COUNT/SELECT pair against `WHERE prompt LIKE ?` with the favorites clause gone from both. The fallback is easy to trigger: line 176 wraps each token in double quotes without escaping, so any token with an odd number of `"` yields a malformed MATCH.

**Failure:** Favorites ticked, search `26"` (a lens, a monitor) or `a 6" figure` → `OperationalError: unterminated string`, swallowed, and the gallery fills with non-favourites while the count badge reports every matching row. Paging then walks a result set the user never asked for. The fallback also changes semantics: FTS ANDs tokens in any order, LIKE demands the whole raw string contiguous, so `a 6" figure` returns zero rows where FTS would have matched. (`50%` alone does *not* trigger the fallback — FTS accepts `"50%"`; the missing LIKE `ESCAPE` only bites alongside an odd quote.)

**Fix.** Delete the second query pair; swap only the search predicate and reuse one helper:

```python
except sqlite3.OperationalError:
    if not search:
        raise
    esc = search.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_")
    where[-1] = "prompt LIKE ? ESCAPE '\\'"
    params[-1] = f"%{esc}%"
    clause = f"WHERE {' AND '.join(where)}"
    total, rows = _page(conn, clause, params, limit, offset)
```

with `_page()` running the same COUNT/SELECT for both branches so filters, ORDER BY and paging can never disagree again. This relies on the search predicate being appended last, which holds today. A faithful fallback should AND per-token LIKEs rather than matching the whole string.

#### `web/app.js:288` — a reload or one transport blip orphans a running sweep

The job id lives only in `currentJob` (46, set at 223, nulled by `setBusy(false)` at 206). Nothing persists it, `/api/status` carries no job field, and the server exposes no enumeration route — only `/api/jobs/{id}`, `/cancel`, `/stream`, all keyed by an unguessable `uuid4().hex[:12]`. `source.onerror` calls `source.close()`, which permanently cancels the browser's automatic reconnect the server was explicitly built to serve (`jobs.events()` replays a snapshot and the undrained `job.queue` holds everything emitted while away — the very case CLAUDE.md's `done`-first bullet describes). A disconnect cancels only the StreamingResponse; `_run` keeps `_gate` and the GPU.

**Failure:** F5 during a 64-run sweep. The page shows "ready" and an idle Generate button. Clicking Generate queues a job behind the orphan; its stream delivers only a `status` snapshot with `status: "queued"`, which `app.js:269` ignores, so the text sits at "queued…" for hours. Cancel targets the new job. The orphan is unreachable — Unload does not free it either (the worker holds a local `pipe` and reloads for the next run). Only killing the server stops it; nothing is lost, since images are already committed.

**Fix,** in priority order: (1) in `onerror`, do not `close()` on the first failure — while `readyState === EventSource.CONNECTING` leave the browser's retry alone and give up only after N consecutive failures; (2) persist `job_id` to `sessionStorage` on submit and reattach on load; (3) handle `data.status === 'queued'` so a blocked job says so; (4) add `GET /api/jobs` returning non-terminal jobs for a page that never submitted one. Land the per-subscriber fan-out (unverified, `jobs.py:244`) alongside (2)/(4) — a reconnect that overlaps the old generator otherwise splits the event stream between two readers.

#### `backend/main.py:75` — no Host-header validation: DNS rebinding gives any site read + delete on the API

The app is constructed with no middleware of any kind. Binding to 127.0.0.1 stops off-machine TCP, not a browser on the user's own machine pointed at loopback by a hostile DNS record; once rebound, the attacker page is same-origin and CORS stops applying. An Origin check alone is insufficient — same-origin GETs carry no Origin.

**Failure:** Victim visits `http://evil.example:7860` (TTL-1, re-answered as 127.0.0.1). `fetch('/api/gallery?limit=200')` returns every prompt, seed and filename; a loop of `DELETE /api/images/{id}` over the returned ids drops the rows and unlinks the PNGs. Also reachable: `POST /api/generate` (queue a 64-run sweep) and `POST /api/model/unload`. Impact ceiling is the user's own gallery — no token or credential is served (`local-krea-read.token` and `krea.db` sit outside both StaticFiles mounts). Chrome's Local Network Access gate catches the rebound loopback request; Firefox and Safari do not.

**Fix.**

```python
app.add_middleware(TrustedHostMiddleware, allowed_hosts=["127.0.0.1", "localhost"])
```

immediately after line 75 — Starlette strips the port before comparing, and the UI fetches only relative paths, so nothing breaks. Do **not** derive the list from `settings.host`: with `KREA_HOST=0.0.0.0` the browser sends the machine's LAN IP or hostname, never `0.0.0.0`. Add a `KREA_ALLOWED_HOSTS` setting for that case. Keep *not* adding a permissive `CORSMiddleware` — its absence is currently the only thing blocking the plain (non-rebinding) cross-origin version of this attack.

### LOW

#### `backend/main.py:114` — body-less POSTs are CSRF-able

`POST /api/model/unload` and `POST /api/images/{id}/favorite?value=false` take no body — `value` is a query parameter — so a cross-origin `fetch(..., {mode:'no-cors'})`, or for favorite even a plain `<form method="POST">`, is a CORS-simple request the server executes. `/api/jobs/{id}/cancel` is *not* blindly exploitable (48-bit random id, opaque response), and `/api/generate` is closed because FastAPI 0.141's `strict_content_type=True` refuses to JSON-parse a body with a missing or non-JSON content type — which also kills the usual `new Blob([json])` bypass. Damage ceiling: a multi-minute inline reload mid-sweep and a cleared `favorite` column (which exists only in SQLite — `save_image` never writes it to the PNG).

**Fix.** A ~6-line `@app.middleware("http")` that 403s when `request.method not in ("GET","HEAD","OPTIONS")` and an `Origin` header is present and outside `{http://127.0.0.1:{port}, http://localhost:{port}}`. Browsers attach Origin to every cross-site POST; curl and `generate.py` send none, so both keep working.

#### `backend/backends/diffusers_backend.py:257` — negative prompt dropped for 0 < CFG ≤ 1 on Krea2

The guard is `request.guidance_scale > 1.0` — the SD/FLUX true-CFG convention, correct for `FluxPipeline` (`do_true_cfg = true_cfg_scale > 1`), wrong for `Krea2Pipeline`, which enables guidance at `> 0`. In the band `0 < g ≤ 1` the backend strips the negative prompt and the pipeline substitutes `""` and runs the uncond pass anyway. Note the guard saves *nothing*: both pipelines encode the negative only inside their guidance branch, so the "wasting an encoder pass" rationale in CLAUDE.md is wrong for both. At `g = 1.0` Krea's `cond + g*(cond-uncond)` is an effective CFG of 2.0 — real guidance, aimed at an empty prompt. The stored `ImageRecord` still records the negative prompt, so Reuse looks faithful.

**Fix.** Gate on the parameter the pipeline actually exposes:

```python
threshold = 1.0 if "true_cfg_scale" in self._call_params else 0.0
if request.negative_prompt and request.guidance_scale > threshold:
```

Fix the same hard-coded threshold in `web/app.js:123` and `generate.py:219` (which prints "[ignored: CFG is at or below 1]" — actively wrong on Turbo), and correct CLAUDE.md lines 40-41.

#### `backend/jobs.py:216` — per-image seed offset skips the 63-bit wrap guard

Line 197 wraps the run seed (`% (_MAX_SEED + 1)`, comment: "Wrap rather than overflow the signed 64-bit seed column"); line 216 passes a bare `seed + offset`. With `seed ≤ 2**63-1` and `num_images ≤ 8`, the stored value reaches `2**63 + 6`. `torch.Generator.manual_seed(2**63)` is accepted and `save_image` writes the PNG *before* the INSERT, so generation succeeds and only the DB write raises `OverflowError`. `generate.py:320` is identical. Reachable only from an exact-int HTTP body or `--seed` (the UI coerces through a JS double and cannot express it).

**Failure:** `--seed 9223372036854775807 --batch 2` → image 0 saved, image 1 written to disk then `OverflowError`, job status "error", remaining runs abandoned, one untracked orphan PNG.

**Fix.** Wrap in all three places, or the recorded seed stops matching the seed used:

```python
# a shared helper, e.g. backend/jobs.py
def wrap_seed(s: int) -> int: return s % (_MAX_SEED + 1)
```
applied at `jobs.py:216`, `generate.py:320`, **and** `diffusers_backend.py:241`'s `manual_seed`. Wrapping only at the storage call would record seed 0 for an image drawn at `2**63` — a fresh reproducibility break.

#### `backend/storage.py:265` — clear_history's orphan sweep collides with in-flight saves

`save_image` opens the PNG at line 140 and holds the handle for the whole encode (~240 ms for a 2048² at `compress_level=4`), committing the row only afterwards; `clear_history` snapshots `keep` at 263 and unlinks every untracked `*.png`. `_write_lock` is a per-process `threading.Lock` and `clear.py` is a separate process. Line 267 unlinks with neither `missing_ok` nor `except OSError`, unlike its siblings at 218 and 258.

**Failure:** running `python -m backend.clear --yes` during a sweep. The likely outcome is `PermissionError [WinError 32]` escaping into `clear.py:100` *after* the row DELETE committed — `vacuum()` never runs, remaining orphans stay, and the user sees a traceback instead of the summary. The narrower window (handle closed, INSERT not yet committed) deletes a good image and leaves a tracked row whose `/outputs/<name>.png` 404s forever, unreachable by any future sweep. `summarise()` at 234 has the same shape with an unguarded `stat()`.

**Fix.** Write to `<name>.png.part` and rename after the INSERT commits — this closes both windows and stops in-flight files inflating `orphan_files`. (An mtime heuristic does not: a file being streamed by the `/outputs` mount is still locked.) Independently, `try: path.unlink(missing_ok=True) except OSError: continue` at 259 and 267, and guard the `stat()` sum at 234.

#### `web/app.js:325` — `loadGallery()` has no in-flight guard

It reads module-level `offset` when building the query (326) and advances it only after the await (337). Nothing serialises calls: `els.more.onclick = loadGallery` (460) never disables the button during the fetch, `#lb-next`'s `disabled` is recomputed only in `renderLightbox` after the await, and `stepLightbox()` awaits it from a keydown handler. Two overlapping calls issue the same offset, both append, and `offset` advances twice. Note `refreshStatus` (162) already carries exactly this guard — it is absent here specifically.

**Failure:** double-click "Load more" (or `#lb-next`) → 48 duplicate cards, `offset` jumps 48→144, the next page fetches 145-192, and images 97-144 are never shown; `openLightbox`'s `list.indexOf(rec)` always finds the first copy. A no-timing variant: the stream's `done` handler calls `resetGallery()` (283), which zeroes `offset` and rebinds `galleryRecords` while a page is in flight, so the stale unfiltered response lands in the reset grid. Self-heals on the next reset.

**Fix.** In-flight promise reuse plus a generation token:

```js
let galleryPending = null, galleryEpoch = 0;
function resetGallery() { galleryEpoch++; offset = 0; ... }
function loadGallery() {
  if (galleryPending) return galleryPending;
  const epoch = galleryEpoch;
  galleryPending = (async () => { const page = await api(...);
      if (epoch !== galleryEpoch) return;   // superseded by a reset
      ... })().finally(() => { galleryPending = null; });
  return galleryPending;
}
```

Also disable `els.more` and `els.lbNext` for the duration, and re-derive the target index in `stepLightbox` after its await.
