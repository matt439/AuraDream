# Code review — 2026-09-07

Multi-agent review of the whole repo at commit `c7331fb`. No code was changed;
this is a record of findings only.

**Method.** 24 finder lenses over 38 files, plus 15 regression checks and 5
lead-triage batches against the 2026-08-29 review, produced 199 raw findings,
merged to 191. Defects were verified by up to three independent adversarial
lenses — one instructed to *refute*, one to *trace the call path* from an entry
point to the defective line, one to *check against documented intent* — and
improvements by two judges each: is the gap real and worth it, and does it
conflict with a documented constraint. A defect survives only if a majority of
its verifiers failed to refute it; an improvement survives only if neither judge
vetoed it. Up to 2 rounds of completeness critics then hunted what the finders
missed. 172 findings were verified: 109 confirmed defects, 43 confirmed
improvements, 3 disputed, 20 killed, 19 left as unchecked leads. For this
write-up the 109 confirmed defect records — plus the ten regression and lead
records describing the same defects — were merged again to **81 entries**, and
ten improvements that duplicate a defect were folded into it, leaving 33.

**Reading the results.** CONFIRMED findings survived adversarial verification
and carry a concrete failure scenario. DISPUTED means the lenses split, and the
split itself is reported. The **Possible improvements** section is not defects:
it is ranked by value, and each entry carries the effort estimate and the
judges' caveats, several of which materially change the proposed mechanism —
read the caveat before the fix. The unverified section fell outside the

# Krea Local — Review Report

## Verdict

Everything that *makes* images overnight is right. Everything that has to
survive the night, or read it back in the morning, is short — and that is now
the whole shape of this codebase's risk. The grid is the feature the last five
commits were built around, and its edges are all unfinished in the same
direction: the base seed a randomly-seeded grid draws is published nowhere, so
the documented recovery ("reuse any image of that run") resumes onto a shifted
or disjoint seed window; the resume key omits half the reproduction set, so a
batch cell counts as done when one of its four images committed, a
quantizer swap satisfies it silently, and a negative prompt the pipeline never
applied defeats it entirely; one transient OOM at cell 401 discards the other
111 cells; a resumed night fragments across two job ids that the search grammar
cannot rejoin; and the contact sheet that exists to read the matrix back cannot
lay out a negative-prompt axis, blanks itself when a pinned axis is promoted,
and freezes the tab for ten seconds if you press its button without a filter
first. Meanwhile the browser collapses under the scale the backend was built to
produce: the viewer strip pulls ~5 GB of full-resolution PNG into the tab over a
1024-cell night, and there is no thumbnail derivative anywhere in the app.

The secondary theme is the last review's dominant one, and it is the reason to
read the regression table before the findings: **fixes landed at the site named
and not at the class**. Nine of the twelve confirmed findings from 2026-08-29
are genuinely gone, several of them exemplary. Three are half gone, and in each
case the surviving half lives one branch over from the fix: the mu
double-shift now composes with the scheduler's *static* shift instead of its
dynamic one, in the branch written as its own remedy, and the only test covering
that branch pins `shift=1.0`, the single value that hides it; `clear_history`'s
orphan sweep still snapshots the row list *before* it scans the directory, so
the window moved rather than closed; and the `loadGallery` re-entrancy guard
now drops the filter change it was supposed to serialise, leaving the gallery
permanently empty. Sixteen of the previous review's unverified leads are still
live, the accessibility cluster untouched in full.

Fix the base seed and the resume key first — a grid you cannot continue, or
that silently continues onto the wrong seeds, wastes GPU-nights rather than
seconds — then the two front-end scale bugs, then the mu fallback before anyone
points `KREA_MODEL_ID` at an SD3-family repo.

## Confirmed findings

### HIGH

#### `web/app.js:531` — appendResult loads every image of a sweep at full resolution, uncapped

`appendResult` builds the viewer's `<img>` with `img.src = rec.url` — the
full-resolution PNG — and, unlike the gallery card (599) and the sheet cell
(926), sets no `loading` attribute. Nothing trims the strip either: `clearResults()`
runs only on the first image of a new job, so the viewer accumulates one
eagerly-fetched full-res `<img>` per image the job produces — up to 512 for a
plain request and up to `max_grid_images` = 1024 for a grid. `.viewer.many img
{ max-height: 20vh }` shrinks the display box, not the download or the decode.

**Failure:** the flagship use case, a 1024-cell overnight grid at the 4 MP tier.
Measured with Pillow at the code's own `compress_level=4`, a representative
2048² output is 5.08 MB encoded and 16.8 MB decoded, so the tab fetches ~5.2 GB
over loopback and holds 1024 live `<img>` elements; the 1 MP tier is still
~1.4 GB. By morning the tab is unresponsive or killed, and the fetches contend
for the disk the generation thread is writing the next PNG to. The reattach path
is a sharper burst: `events()` opens with a snapshot carrying every image made
so far and `onmessage` does `data.images.forEach(show)`, so a reload at cell 900
appends 900 eager full-res images in one synchronous pass — and the recovery the
code itself prints ("reload to pick it up") is the action that triggers it.

**Fix.** Two lines and a cap in `appendResult`: `img.loading = 'lazy';
img.decoding = 'async';` and `while (els.viewer.children.length > VIEWER_MAX)
els.viewer.firstElementChild.remove();`. Keep pushing every record into
`viewerRecords` so the lightbox still walks the whole run, and put any "… and N
more this run" note *outside* `#viewer`, or the cap loop and `clearResults()`
will eat it. Lazy alone is not enough — `.viewer img` sets no height, so
unloaded images stack inside the viewport and all become eligible at once; the
DOM cap does the work. Pairs with the thumbnail derivative (`app.js:597`).

#### `web/app.js:918` — renderSheet crosses two unbounded axes and rescans all records per cell

`renderSheet` lays out `colValues.length × rowValues.length` cells, where each
axis is the distinct values the loaded records take, and for every cell runs
`sheetRecords.find((r) => matches(r, rowValue, colValue))` over up to 1024
records. Nothing caps the product. Seeds are unique per image by construction,
so `values.seed.length` equals the page size for any set that is not one grid's
seed axis, and `chooseAxes` sorts by distinct count descending — so seed always
wins the columns slot on a mixed gallery. `matches` compounds it: it allocates
`Object.entries(sheetAxes.pins)` and calls `axisByKey` — itself a
`SHEET_AXES.find` — up to five times per record per cell. The trigger is the
invited action: the Sheet button with the search box empty, whose title reads
"Arrange these images by their settings".

**Failure:** running the verbatim `SHEET_AXES`/`sheetValues`/`chooseAxes`/
`matches`/cell-loop code under Node 24 against 1024 synthetic records, 60
distinct prompts gives 61,440 cells and **1.55 s** of matching alone for 171
non-empty cells; 400 distinct prompts gives 409,600 cells and **9.97 s**. That
is JIT-warmed JS with no DOM. On top of it the loop appends 61,440–409,600
`<div>`s and sets `gridTemplateColumns` to `auto repeat(1024, minmax(96px,
1fr))` — a grid at least 100,000 px wide. The escape route re-triggers it: each
keystroke of the `job:` filter that would fix the layout costs another 1024-row
fetch and another full render per 250 ms debounce tick.

**Fix.** Any one of three defuses it; all three are worth having. (1) Refuse
past ~4096 cells with a note telling the user to filter to one run — the ⊞
button on a card sets `job:…`. (2) Index instead of scanning: one pass into a
`Map` keyed by row and column value turns O(cells × records) into O(records +
cells). (3) Hoist the pins and `axisByKey` lookups out of `matches`. Also make
`chooseAxes` skip an axis whose distinct count equals `records.length` — an axis
with one value per image is a list, not a dimension.

#### `backend/grid.py:348` — a grid's drawn base seed is published nowhere, and the documented recovery resumes onto the wrong seed window

`grid.expand()` draws the base seed itself when the request has none, and every
cell then carries a *derived* seed, `wrap_seed(base + index * num_images)`. The
base is never surfaced: `/api/grid` returns only `JobAccepted(job_id=...)`,
`Job.snapshot()` has no seed field, the per-cell label is steps/CFG/mu, and
`web/app.js` never writes anything back into the Seed box after a submit.
Resume is nevertheless refused without an explicit seed, so the base seed is the
one thing a resumed night cannot do without. All three places that tell the user
how to recover it give the same wrong instruction — `web/index.html:179`,
`README.md:296` and the 422 body at `backend/schemas.py:102` all say to reuse
*any* image of that run, which is correct only for `seeds == 1`. The gallery is
ordered `id DESC`, so the image nearest to hand is the newest: the highest seed
the night reached, not the base.

**Failure:** run against the repo's own code (`steps_axis="6,8"`,
`cfg_axis="1,2"`, `seeds=4`, base 1000, night dies after 2 seeds). With
`num_images=1`, resuming from the newest image (seed 1001) expands to seeds
1001–1004 and renders 1002, 1003 and **1004** — a seed the grid never contained
— 12 cells instead of the 8 outstanding. With `num_images=2` (cell seeds 1000,
1002, 1004, 1006; saved image seeds 1000–1003), resuming from the newest image
(seed 1003) expands to cell seeds **1003, 1005, 1007, 1009**, disjoint from the
original: `prune_done` drops 4 of 16, renders 12 cells at seeds that answer no
question, and the grid's own remaining seeds 1004 and 1006 are never rendered.
The only way to get the true base today is to filter `job:<id>` and page to the
*oldest* row — 22 clicks of "Load more" for 1024 images. The CLI has none of
this problem: it prints the drawn seed before the run.

**Fix.** Publish it. Add `seed` to `Job.snapshot()` and to `JobAccepted` —
`run_grid` already has `cells` in hand, so `JobAccepted(job_id=job.id,
seed=cells[0].seed)` is one line, and `submit()` should do the same for a plain
sweep — then in `startJob()` write it into an empty Seed box after the POST, and
include it in `/api/jobs` rows. Fix the instruction in all three copies to say
the *first/oldest* image, and note that with batch > 1 only the first image of a
batch carries a cell's seed. Optionally 422 a resume whose seed matches no
`cell_key` in `completed_cells()`. **CLAUDE.md's resume bullet and its "reuse it
from any image" corollary are the passage that has to change:** keying on
settings is right, but the seed is the one setting the client is never given
back.

### MEDIUM

The grid and its recovery path account for eight of these; they are listed

#### `backend/grid.py:227` — the prompt axis's cartesian product is materialised before any ceiling is checked, on the event loop

`prompt_assignments()` builds the entire product of the prompt variables as a
real list of dicts before anything counts it. `MAX_AXIS_VALUES = 64` caps values
*per variable*, never the number of variables or their product, and the only
whole-grid ceiling is computed from `len(assignments)` — a number that exists
only once the list has been built. `main._expand` makes it worse: it calls
`grid.axis_values(...)` and then `grid.expand(...)`, and each calls
`prompt_assignments()`, so the product is materialised two or three times per
request. Both grid endpoints are `async def` calling `_expand` inline, in
contrast to `storage.step_cost_ms` two lines later, which is correctly wrapped
in `asyncio.to_thread`.

**Failure:** `prompt_axis` allows 2000 characters and a variable line costs ~7,
so ~280 binary variables fit. Measured: 18 variables (287 chars) = 262,144
assignments in 1.14–1.38 s; 20 = 1,048,576 in 3.06 s at 743 MB peak; 4 variables
× 32 values took 0.90 s and 208 MB to build, then 7.28 s and 271 MB to
substitute. Through HTTP an 18-variable axis blocked for 1.38 s and then
answered 422 "past the 1024 a grid may queue". The UI fires
`/api/grid/preview` on a 250 ms debounce from every keystroke in that textarea,
so typing a block walks the product up one doubling at a time — and because it
is the event loop the freeze is server-wide: SSE progress stops, `/api/status`
stalls, and `POST /api/jobs/{id}/cancel` cannot be served, so an overnight sweep
running at the time cannot be stopped and a MemoryError takes it down with the
process. The guard that exists to refuse this cheaply never gets to run.

**Fix.** Count before building, in `prompt_assignments` after the placeholder
checks: `count = math.prod(len(v) for v in variables.values())`, raise
`ValueError` past `settings.max_grid_images` — `grid.py` already imports
`settings` and `_expand`'s `except ValueError → 422` needs no change. While
there, have `_expand` pass the resolved axes into `expand()` instead of
resolving twice, and consider `await asyncio.to_thread(_expand, request)` so a
large-but-legal grid cannot stall the loop either.

#### `backend/backends/diffusers_backend.py:411` — `_shifts_itself` treats "not dynamic" as "no shift", so the fallback composes into `mu + ln(shift)`

`_shifts_itself()` answers only `scheduler.config.use_dynamic_shifting`. When
that is False the backend pre-shifts the ramp itself and blanks mu. But
`use_dynamic_shifting: false` does not mean no shift:
`FlowMatchEulerDiscreteScheduler.set_timesteps` is an if/else, and the else
branch applies `sigmas = self.shift * sigmas / (1 + (self.shift - 1) * sigmas)`
— which multiplies the odds `s/(1-s)` by `shift`, exactly as the exponential
branch multiplies them by `e^mu`. The two compose. This is the same additive
composition as the 2026-08-29 review's top finding, surviving inside the branch
written as its fix, and `_shifted_sigmas`'s docstring ("only used for a
scheduler that does *not* shift on its own") is true only at `shift == 1.0` —
which is exactly what `tests/test_schedule.py:109` passes, so the only test
covering this branch passes whether the backend compensates or not.

**Failure:** driving `generate()` through the repo's own StubPipeline with
`FlowMatchEulerDiscreteScheduler(use_dynamic_shifting=False, shift=3.0)` and
mu=1.15, the landed sigmas are `[1.0, 0.9851, 0.9660, 0.9404, 0.9045, 0.8504,
0.7595, 0.5751]` against the intended `[1.0, 0.9567, …, 0.3109]` — matching
`_shifted_sigmas(8, 1.15 + ln 3)` to 1e-5. Reachable on any checkpoint with
`use_dynamic_shifting: false` and `shift != 1.0`; SD3/3.5 ship 3.0 and Lumina 2
ships 6.0, and both `launch.py`'s "another repo id" option and the module
docstring's "any other diffusers text-to-image repo" invite exactly that. Every
image then runs at an effective 2.25 while `ImageRecord.mu` records 1.15, so
Reuse reproduces the same wrong schedule and a mu sweep compares points all
offset by `ln(shift)`. The three catalogue families are unaffected.

**Fix.** Subtract the shift the scheduler will apply anyway, the way `_forced_mu`
already replaces the mu the pipeline would have derived: read `shift` off the
scheduler *instance* (`set_timesteps` uses `self.shift`, not
`self.config.shift`) and pass `_shifted_sigmas(steps, mu - math.log(shift))`.
At `shift == 1.0` that is byte-identical to today. Parametrize the fallback test
over `shift in (1.0, 3.0)` — it fails today at 3.0 — and drop its
`assert pipe.sigmas_arg == …` line, which asserts the list the backend computed,
exactly what CLAUDE.md says not to assert on. **Correct the CLAUDE.md bullet:** a
non-dynamic scheduler still shifts, statically. While there, `shift_terminal`
and the three alternative sigma schedules also post-process in both branches; a
warning when any is set would stop mu quietly meaning something else again.

#### `backend/grid.py:216` — a prompt full of `{placeholders}` with an empty variables box escapes the grid's own mismatch guard

`prompt_assignments()` returns `[{}]` *before* it computes `used =
_placeholders(request)`, so the two mismatch checks that follow never run when
the variables block is empty, and `substitute(text, {})` returns the prompt
unchanged. Three documents assert this cannot happen: CLAUDE.md ("a placeholder
with no variable renders the literal `{ground}` into every image of the run"),
README ("Both are caught when you submit, not at 3am"), and
`tests/test_grid.py`, whose five parametrised mismatch cases all supply at least
one variable — so the hole is exactly the case the suite does not reach.
`_placeholders` reads the negative prompt too.

**Failure:** verified at HEAD — expanding a request whose prompt is `{size} dog
sitting on {ground}` with an empty variables block yields 4 cells all carrying
the literal braces, while the same request with `size = big | small` is
correctly refused. The browser gives no other signal: `promptLines()` returns
`[]` below two prompts, so the preview shows only the image count. The easiest
mistake in the feature — writing the placeholders and forgetting the box, or
clearing the box while keeping the prompt — produces a full-length overnight run
in which every image was conditioned on literal braces: a 480-cell night is four
hours of GPU time and 480 useless PNGs, all committed, all counted as done by
`--resume`, and indistinguishable on the contact sheet.

**Fix.** Compute `used` first and, when there are no variables, raise if it is
non-empty. That keeps "a grid with no axes set is exactly the image Generate
would have made" for a prompt with no placeholders, which is what index.html's
"Blank runs the prompt exactly as written" is about. Add the missing
parametrised case. If a literal `{WORD}` must stay possible, add an escape
rather than keeping the silent path.

#### `backend/grid.py:298` — resume marks a whole batch cell done when only its first image committed

`cell_key()` identifies a cell by `cell.seed` — the *base* seed —
`completed_cells()` builds its key set from one row per *image*, and
`jobs._generate` writes each image under `wrap_seed(seed + offset)`. With
`num_images == 1` they coincide; above that only image 0's row can ever match a
cell key, so one committed row declares the whole cell rendered. Nothing counts
rows per cell.

**Failure:** verified with no GPU — seed 1000, `num_images=4`, steps `8,10`,
2 seeds gives cells at (8,1000), (10,1000), (8,1004), (10,1004); feeding
`prune_done` a `done` set containing only `cell_key(cells[0])` drops cell
(8,1000), which should have produced seeds 1000–1003. Operationally: a grid with
Batch 4 stops between saves at 03:00 (power cut, disk full, a transient
"database is locked" from a backup tool or a concurrent `clear.py` VACUUM). In
the morning the user ticks Resume and re-submits the identical grid as README
instructs; the cell is skipped and images 1–3 are never rendered. The contact
sheet still shows a picture in that square, so the hole is invisible there too.

**Fix.** Make the completeness test cover the whole batch: `cell_keys(cell,
num_images)` returning one key per per-image seed, and `prune_done(cells, done,
num_images)` keeping a cell unless every key is present. `main._expand` passes
`request.num_images`, `generate.main` passes `args.batch`; `completed_cells`
needs no change. Add a test that a `done` set holding only the base seed of a
4-image cell does not prune it.

#### `web/app.js:614` — a resumed night is split across two job ids, and the contact sheet can only ever show one half

`submit_cells` mints a fresh id per submission and `save_image` stamps every
image with it, so after one resume the grid's images carry two `job_id`s.
Everything built to read a run back is keyed on exactly one: the card's ⊞ button
hard-codes `els.search.value = 'job:' + rec.job_id`, and the search grammar
cannot express the union — `list_images` AND-joins every predicate, so two
`job:` terms are unsatisfiable and a comma list becomes one LIKE that matches
nothing (confirmed against the shipped parser). The settings-based workaround is
worse than nothing: a search spanning both halves drags in every earlier image
at those settings, and `renderSheet`'s `find` takes the first match in
newest-first order, so duplicate settings silently put the wrong image in the
square.

**Failure:** a 1024-cell grid dies at cell 700, the user resumes as documented,
and the remaining 324 land under a second id. The ⊞ button now yields a sheet of
at most 700 or at most 324 cells with every square from the other half empty and
the note reading "700 of 700 loaded". The complete matrix — the single artefact
the whole grid feature exists to produce — cannot be displayed at all, and a
night interrupted three times fragments into four unjoinable sheets.

**Fix.** Give a grid a stable identity independent of the job that ran it: a
`run_id` column derived on the server from the run's own definition (a hash of
model_id, size, base seed, the sorted resolved axes and the distinct prompts),
computed in `_expand` and passed through `submit_cells` into `save_image`, so a
resume recomputes the same id. Point ⊞ at `run:<id>`, add `run` to `_FILTERS`,
fall back to `job:` for older rows. Smaller stopgap that fixes only the reading
half: let `_filter_clause` OR a comma-separated list for the string filters, and
have `startJob` remember the id it just queued.

#### `backend/storage.py:388` — quantization is not in the record or the resume key

`completed_cells` scopes its lookup to width, height and model_id, and the key
it returns is (prompt, negative, steps, CFG, mu, seed). Quantization and offload
are not in it — and cannot be, because nothing persists them: no column, no PNG
field, nothing on `ImageRecord`. `quantization` appears exactly once in the
whole persistence surface, as `ModelStatus.quantization`, which is live status
rather than history. But it is part of the reproduction set, and config.py says
so itself: fp8 is "~12GB", int8 "smaller still, slightly softer output",
nunchaku SVDQuant W4A4. Same seed, same everything else, different quantizer,
different pixels.

**Failure:** `--seed 42 --grid-cfg 0-4x1 --grid-seeds 4 --quant fp8` queues 20
cells and is killed after 9. The next run is `--resume --quant int8` — or a bare
`python -m backend.main` that takes the fp8 default on a bare Enter after an
int8 night, which CLAUDE.md documents as the menu's behaviour. It prints
"resume : 9 cell(s) already rendered, skipping" and renders the remaining 11
under a different quantizer. The contact sheet whose entire purpose is comparing
CFG across a fixed seed then has 9 cells from one numerical pipeline and 11 from
another, with no column, badge, filter or PNG field distinguishing them.
Independently, Reuse silently produces a different image whenever the server is
on a different quantizer than the run that made the card.

**Fix.** Persist it and key on it: `quantization TEXT` through `_SCHEMA` and
`_migrate` (the `job_id` migration is the precedent), passed into `save_image`
beside `model_id`, into the `krea` chunk and onto `ImageRecord`; extend
`completed_cells` to `AND (quantization IS NULL OR quantization = ?)` so an
existing gallery keeps resuming; add `quant:` to `_FILTERS`. Update the
CLAUDE.md resume bullet to name quantization as part of the key. Offload is
likely bit-identical, so recording it is documentation rather than a key.

#### `backend/backends/diffusers_backend.py:403` — the recorded negative prompt is not the one that ran, and it defeats `--resume`

The backend drops the negative prompt when it cannot apply, and nothing tells
storage: both save paths hand `save_image` the untouched request, which writes
`request.negative_prompt` into the DB row, the `krea` chunk and the A1111
`parameters` block. **This makes CLAUDE.md lines 77–79 false** — "Dropping the
negative prompt below the threshold … only keeps the recorded settings honest
about what ran" — so the guard now delivers nothing. The two configurations
where it bites are both *profile defaults*: Krea 2 Turbo (threshold 0.0, profile
guidance 0.0, so `0.0 > 0.0` is False) and FLUX.2 klein (unsupported; the code
even logs "ignoring it"). All three clients feed it — `collect()` reads a
disabled textarea, `generate.py` prints "[ignored…]" and passes the string
anyway, `/docs` has no filter. The same shape hits `mu`: on a pipeline with no
`sigmas` parameter and a non-shifting scheduler, mu is blanked and the kwarg
popped, yet `request.mu` is still written.

**Failure:** Turbo at profile defaults. Night 1 is a 16-cell grid with
negative_prompt "blurry, low quality"; the pipeline never sees it, all 16 rows
record it, the run dies at cell 9. Next morning the user notices the field is
greyed at CFG 0, clears it, ticks Resume, re-submits with the same seed. Every
`cell_key` now carries `None` where every row carries the string, so
`prune_done` matches nothing: the preview says 0 already done and the job
re-renders all 16 cells, 8 of them pixel-identical duplicates at full GPU cost.
The mu variant is worse, because mu *is* in the key: an image made with no shift
at all is recorded as mu=1.15, so `mu:none` never finds it and `prune_done`
treats a mu=1.15 cell as already rendered.

**Fix.** Make the two sides agree on one normalisation. Smallest self-consistent
version: `collect()` sends `negative_prompt: els.negative.disabled ? null : …`,
and `generate.py` reuses the branch that already decides its note. The complete
version has the backend report what it applied — it already computes `supported`
and `threshold` — with both save paths storing
`req.model_copy(update={…})`; `main._expand` must then normalise cell keys the
same way before `prune_done`, falling back to the profile's guess when no
pipeline is loaded. Correct CLAUDE.md 77–79 in the same change, and add `mu` to
the A1111 block for the reason that block exists.

#### `web/app.js:172` — the negative-prompt gate is computed from the panel's single CFG

`syncCfg()` disables the textarea whenever `+els.cfg.value <= cfgThreshold`,
with two consequences in opposite directions. A grid's CFG axis decides guidance
*per cell* — `gridPayload()` spreads `collect()` and `grid.expand` builds each
cell with its own `guidance_scale` while inheriting `negative_prompt` — but the
gate reads only the panel value. And `collect()` reads `els.negative.value` with
no reference to that gate at all, so a disabled, greyed-out field still ships
its contents. This is the previous review's unverified `app.js:187` entry, still
unfixed, and klein makes it permanent.

**Failure:** Turbo, panel CFG 0, grid CFG axis `0,0.5,1` — which is the literal
placeholder in `index.html`. The textarea is disabled, so the two guided cells
of every comparison run against no negative prompt and there is no way from the
UI to give them one, which is precisely the comparison a CFG sweep is for; the
note under the field reads "(needs CFG > 0 — ~2× slower)" while describing a run
that crosses that threshold. Reading the sweep in the morning, the user
attributes the jump between the CFG 1 and CFG 2 columns to guidance strength;
half of it is the negative prompt switching on, and neither the column headers
nor the lightbox nor the PNG says so.

**Fix.** Gate on the highest CFG the submission can reach — when the grid
section is open and the axis is non-empty, take the max of the resolved values,
which the preview response already carries — and make `collect()` honour the
gate it draws. The server-side half is the entry above.

#### `web/app.js:695` — Reuse restores a record's checkpoint-specific settings onto whatever checkpoint is loaded

`reuse(rec)` restores prompt, negative prompt, size, steps, CFG, mu and seed,
and never looks at `rec.model_id`. It cannot: unlike `cfgThreshold` and
`negativeSupported`, which are kept in module state precisely so the page can
consult them, the loaded checkpoint is never stored — `refreshStatus` reads
`s.model_id` only to build the status-bar text. The gallery is one index shared
by every checkpoint and the launch menu makes switching a start-up question, so
it routinely holds Turbo rows (8 / 0.0 / 1.15) beside FLUX rows (28 / 3.5 /

#### `backend/main.py:92` — Ctrl-C cannot stop a running sweep

`jobs.shutdown()` is the only thing that sets `cancel_requested` at exit, and it
is called from the lifespan shutdown — which uvicorn runs *last*.
`Server.shutdown()` first calls `connection.shutdown()` on every open connection
(for an in-flight response that only sets `keep_alive = False`; it does not
close the transport), then awaits `_wait_tasks_to_complete()` with
`timeout_graceful_shutdown`, which `main.run()` never passes and which defaults
to `None`, i.e. unbounded. That wait spins while connections remain, and the
browser's EventSource will not complete until `jobs.events()` yields `done`,
which only happens when the job finishes. The cancel that is supposed to stop
the sweep is queued behind the sweep.

**Failure:** start a 1024-cell grid with the tab open and press Ctrl-C. The log
prints "Shutting down" then "Waiting for connections to close. (CTRL+C to force
quit)" and sits there for the rest of the grid — hours. Press Ctrl-C again:
uvicorn sets `force_exit`, breaks the wait, and *skips the lifespan call
entirely*, so `jobs.shutdown()` and `backend.unload()` never run; `serve()` then
returns with a non-default ThreadPoolExecutor still executing `_generate`, which
`concurrent.futures.thread._python_exit` joins at interpreter shutdown — and
`_generate` is one work item covering all of the job's cells, so the join waits
for the entire remaining grid. Neither keystroke stops anything. With no browser
attached the documented behaviour works, which is why this survives casual
testing; the docstring at `jobs.py:120` claims this path prevents exactly the
hang it cannot reach.

**Fix.** Set the flag on the signal, before uvicorn starts draining: subclass
`uvicorn.Server`, override `handle_exit` to set `cancel_requested` on every
`jobs.active()` job, then call `super()`. It then fires on both the first and
the forced Ctrl-C, the worker unwinds within one step, `done` is emitted, the
stream returns and the normal drain completes. Pass
`timeout_graceful_shutdown=30` for a client that stops reading, and keep
`jobs.shutdown()` in lifespan as the join.

#### `backend/main.py:93` — Ctrl-C during a model load freezes the event loop until the load finishes

`lifespan` calls `backend.unload()` synchronously on the loop, not through
`asyncio.to_thread` the way `unload_model()` does. `unload()` opens with `with
self._lock:` *before* the `if self._pipe is None: return` check, and `load()`
holds that same lock for its entire body. So during a load, shutdown blocks the
loop inside a C-level lock acquire purely to discover there is nothing to
unload. A second Ctrl-C cannot rescue it: uvicorn gates the lifespan call on `if
not self.force_exit`, a check that has already passed, and `handle_exit` only
sets a flag nothing will read because the loop is not running. `jobs.shutdown()`
gives no cover — a job blocked in `await self._ensure_loaded()` was never
submitted to the pool.

**Failure:** `KREA_PRELOAD=true`, no browser open (also reachable via a
curl-triggered load, or by closing the tab during one). Four minutes into the
download the user realises it is the wrong repo and presses Ctrl-C. uvicorn logs
"Shutting down" and the process then does nothing — no further log lines, no
prompt — until the whole multi-GB load completes, which per CLAUDE.md's note
about the xet downloader stalling a 12 GB checkpoint is not bounded. Repeated
Ctrl-C has no effect; the only way out is killing the process, which risks
leaving an uncollectable `.png.part`.

**Fix.** `await asyncio.to_thread(backend.unload)` at minimum. Better, a
`try_unload()` using `self._lock.acquire(blocking=False)` that returns
immediately if the loader holds it — the process is exiting, so freeing VRAM
buys nothing. Independently, give `load()` a way to be abandoned (a
`threading.Event` checked between component loads) so "stop this load" is
expressible at all.

#### `backend/jobs.py:265` — one cell's exception abandons every remaining cell of a grid

The cell loop catches exactly one exception, `except Cancelled`, and
`save_image` is not inside any `try` at all. Everything else escapes the loop,
is caught once in `_run`, sets status `error` and emits the terminal event — and
the remaining cells are silently discarded, the list simply never iterated
further. That is the opposite of what the cancellation path two lines above
does, and of what CLAUDE.md promises for it. An exception is treated as fatal
even for failures that are transient and cell-local: a CUDA OOM when another
process briefly takes VRAM, or `database is locked` from a concurrent
`clear.py`. `generate.py` has the identical shape.

**Failure:** a 512-cell grid at 2 MP, six hours in, 400 cells rendered. At 02:00

#### `backend/storage.py:211` — `save_image`'s cleanup handler deletes the finished image when the rename fails

The guard is `except BaseException: _unlink(partial); raise`, but the `try`
spans two very different things: the INSERT and the rename. `_session()` commits
on leaving `with conn:`, so by the time `partial.replace(path)` runs the row is
durable — and if the rename raises, the handler deletes the only copy of the
image while the row stays in the database. The comment reasons only about "a
failed INSERT"; it has no way to tell the two cases apart.

**Failure:** reproduced by making `Path.replace` raise `PermissionError(32)` —

## Disputed

Three findings split their lenses. In each case the split is over exposure or
mechanism, not existence.

- **`backend/main.py:93` — lifespan's synchronous `backend.unload()`.** Both lenses agree the loop is frozen for the remainder of an in-flight load, and that uvicorn's `if not self.force_exit` gate makes a second Ctrl-C useless once lifespan has been entered. They split on reach: with any client connection open, uvicorn's drain runs first and `force_exit` lands before lifespan, so the hang needs a load in flight *and* no open connection — `KREA_PRELOAD`, a curl-triggered load, or a tab closed mid-load. Reported in full as a confirmed MEDIUM; the disputed narrowing is the exposure, and `await asyncio.to_thread(backend.unload)` settles the blocking half either way.
- **`backend/storage.py:184` — a failed PNG encode leaving a `.png.part`.** Both agree a hard kill mid-encode leaks a partial nothing collects (reported as confirmed LOW). The refuting lens verified against the installed Pillow that `Image.save` already removes a file it created when the encoder raises `Exception`, so the ENOSPC framing in the original finding does not occur — and that also kills the proposed `Image.verify()` sweep as an unbounded read for a condition that cannot arise. What survives is `KeyboardInterrupt`: `BaseException`, so Pillow's own handler misses it, and the CLI's second Ctrl-C raises exactly that on the thread calling `save_image`, which then exits 0 with the partial left behind. Moving the encode inside `storage`'s own `except BaseException` is correct either way.
- **`web/app.js:373` — the grid preview has no request-ordering guard.** `previewGrid` writes its response unconditionally, with no token and no abort, while the same file solves exactly this for the gallery. The lenses split on whether responses can actually overtake: `preview_grid` does the expensive work synchronously and then awaits `step_cost_ms` off-thread, which is a real yield point, so a slow request that got in first can be overtaken across that one suspension — a narrower window than the finding implies, but reachable, and `previewGrid` is also wired directly to the `<details>` toggle. Concretely: type `1-64` into Steps with Resume ticked, narrow to `8` before the reply lands, and the panel can end up describing a 1024-cell run the boxes no longer contain. Fix is the epoch token the gallery already has.

## Possible improvements

Not defects: gaps worth closing, ranked by value to someone who runs this most
nights. Each survived two judges — *is the gap real and worth it*, and *does it
conflict with a documented constraint* — and each carries the judges' caveats,
several of which change the proposed mechanism materially. Read the caveat
before the fix. Ten further improvements duplicated a confirmed defect
(thumbnails, the eager viewer strip, the quadratic status event, the cancel and
CLI test gaps, the per-cell failure handling, the batch budget, the `.png.part`
accounting) and were folded into those entries instead.

**1. `backend/main.py:291` — nothing says what happened to last night's run.** *(medium)*
`active_jobs()` returns only non-terminal jobs and `resumeActiveJob()` silently
does nothing when the list is empty, so the morning after you get an idle
Generate button and a gallery with 299 images in it, and nothing anywhere says
the 480-cell grid stopped at cell 300, when, or why. The error string exists on
the Job and the object is still in `_jobs` — it is never served; after a restart
even that is gone, though every image carries `job_id` and `created_at`. Two
mechanisms: a `storage.runs()` GROUP BY behind `GET /api/runs`, surfaced as a
Runs selector that sets `job:<id>` and switches to the sheet; and an
`include_finished` flag so the page can report the newest terminal outcome.
*Caveat:* the banner is in-memory, so it answers "why" only while the failing
server is up; the DB half answers "how many and when" and never "why". A
`job_id`-keyed list splits a resumed grid into two rows, so it wants the
`run_id` fix first. `/api/jobs` deliberately strips `images`, so take the
run/total_runs counters; do not reattach `streamJob` to a terminal job to get
the message for free (it would dump 299 images into the viewer on every load);
gate the banner so a three-day-old OOM is not re-announced forever; and fix the
"cancelled" status defect first or the banner will misreport a finished run.

**2. `web/style.css:371` — the lightbox cannot zoom, so the comparison an overnight grid exists to make cannot be made in the app.** *(medium)*
The whole image display is `max-width: 92vw; max-height: 78vh; object-fit:
contain`, so a 2048² image is always shown at ~40%, with no zoom, pan or 1:1 —
and the sheet is 96 px with `object-fit: cover`. A steps or mu sweep is a
question about fine detail, and at 40% every cell looks the same, so the only
way to answer it is to leave the app for an external viewer that knows nothing
about which cell is which. A pure `web/` change; the load-bearing part is *not*
resetting zoom and pan between records of the same size, so the arrow keys
compare the identical crop at the identical magnification across cells.
*Caveat:* four mechanics decide whether it feels broken. The stage must be
`flex: 1 1 auto; min-height: 0`, not a hard 92vw/78vh, or flex shrinking plus
`overflow: hidden` clips the fit view. A full-size stage swallows the backdrop
click that currently closes the lightbox — decide that explicitly. "1:1" must
divide by `devicePixelRatio`, or Windows scaling makes it a 1.25–1.5× resample,
precisely the smoothing a sharpening sweep is judging. The wheel handler must be
non-passive, and the new keys must sit *below* the existing `input, textarea`
guard, since focus is never moved into the lightbox. Nearer 100 lines than 60,
with no frontend test suite behind it.

**3. `backend/generate.py:317` — CLI grids print a cell count but no time estimate.** *(small)*
`/api/grid/preview` computes `seconds` from `step_cost_ms` and the panel renders
"about 4h 12m"; the CLI's settings block stops at the image count, and
`step_cost_ms` is not called anywhere in `generate.py`. So the one interface
actually used for unattended overnight work is the one that will not tell you
whether the run finishes before morning — and knowing a grid is fourteen hours
is what makes you drop an axis before committing the night.
*Caveat:* do not add a third copy of the arithmetic — put it in one helper both
`preview_grid` and the CLI call, keeping the "no rows, no estimate" rule. Add
the `model_id` predicate `step_cost_ms` is missing at the same time, or a klein
median prices a Turbo run at half. Guard with `db_path.exists()`, since
`step_cost_ms` goes through `_connect` and would write the schema into any file
it opens. Word it as generation time, not wall clock — the CLI pays a load every
invocation — and give `_duration` an hours branch, or a four-hour grid renders
as "252m30s".

**4. `backend/main.py:254` — no way to re-render a night's winners at full size.** *(small)*
The documented workflow ends at "star the winners". `reuse(rec)` restores one
image's settings, one image at a time, and the user retypes the size — twenty
favourites is twenty round trips, and the clicking is the expensive half,
because it is where a seed gets mistyped. Every part exists: `ImageRecord`
carries the complete reproduction set by design, `submit_cells` explicitly takes
an already-expanded list of pipeline calls, `list_images(favorites_only=True,
search='job:…')` returns exactly the set, and `completed_cells` keys on size so
a 2K re-render cannot collide with the 1 MP grid it came from. A sibling of
`run_grid`, ~30 lines.
*Caveat:* it must call `check_budget()` — 2816² passes the schema and is 1.8×
past the pixel budget, and both existing producers make that call. There is no
"current selection" in the UI and `galleryRecords` holds only the paged-in 48,
so take the gallery's own filter server-side or fetch the ids first and put the
count in the button. Dedupe with `completed_cells` + `prune_done` and 409 when
nothing is left. Batch the lookup. And be honest about what it delivers: the
pipeline draws latents at the requested shape, so the same seed at 4 MP is a new
sample — the prompt and settings carry, the picture does not. For a
prompt-variable grid that is the whole value; for a seeds-only grid the
selection is thrown away.

**5. `tests/test_schedule.py:40` — the scheduler stub never calls back, so the backend's progress, cancel and generator code is executed by no test.** *(small)*
`StubPipeline` accepts `callback_on_step_end` and never invokes it, and the
klein stub does the same — and those two are the only things in the suite that
drive the real `DiffusersBackend.generate`. So everything between the kwargs
dict and the return is unexecuted: `_step_end` (simultaneously the only progress
source and the only cancellation point), the per-image generator list, the
silent kwarg drop, and the "not loaded" guard. Three lines in the stub plus a
small `tests/test_backend.py` — six assertions, measured at 1.05 s.
*Caveat:* one claimed benefit is overstated and must not go in the docstring — a
diffusers *rename* of `callback_on_step_end` is not caught, since the stub owns
its own signature; close that separately with a signature assertion against the
real classes, which import fine with no weights. `should_cancel` is polled once
before the pipeline is entered, so assert on the stub's own step counter rather
than the predicate's call count.

**6. `backend/grid.py:78` — the prompt-variable assignment that made each image is thrown away.** *(medium)*
`Cell.variables` is the exact assignment that produced a cell and nothing reads
it; `save_image` gets the substituted request and stores only the finished
prose. So everything downstream reconstructs it from strings: one flat prompt
axis, meaning N variables crossed together collapse into a single axis of N-fold
values — a 2×2 `size`×`ground` night renders as a 4-wide strip, never as the 2×2
it was — and `promptLabels` diffs word positions to recover labels, which fails
outright on the `none` value the UI itself recommends. Persist it (a
`variables TEXT` column via `_migrate`) and append one sheet axis per variable
name seen; `chooseAxes` needs no change.
*Caveat:* **suppress** the flat prompt axis when any record carries variables —
keeping it as a fallback lets a 4-value prompt axis beat a 2-value var axis and
turns a single-variable run into a diagonal sheet, worse than today.
`SHEET_AXES` is a module const read in five places, so rebuild it at the top of
`renderSheet` with the names folded into the signature, and give
`_row_to_record` the same `in row.keys()` tolerance mu and `job_id` carry. Drop
the `var:size=big` search term from scope — it needs a `json_extract` branch,
not the column+cast shape `_FILTERS` has.

**7. `backend/backends/diffusers_backend.py:376` — FLUX.2 klein's reference-image conditioning is already loaded and completely unreachable.** *(medium)*
`Flux2KleinPipeline.__call__` takes `image` as its *first* parameter, resizes
each reference to ≤1 MP, VAE-encodes it and concatenates the tokens onto the
latent sequence every step — native multi-reference image editing, at no extra
weights and no second download. `_call_params` already contains `"image"` when
klein is loaded and the kwargs dict is exactly where it would go, but there is
no request field and no control. The most capable thing on this machine cannot
be used for what it is best at: no "same character, new pose", no iterating on a
gallery image, and no sweeping a prompt axis against a fixed reference.
*Caveat:* the cost is understated — a 1 MP reference roughly doubles the
sequence and quadruples the attention term, so 2–3× per image, not "one VAE
encode". Joining a raw request string onto `outputs_dir` is an arbitrary-file
read reachable from `/api/generate`; resolve through the images table instead.
The module imports `Image` as the *class*, so the open needs a local import.
Publish the capability the way `negative_prompt_supported` is published and
refuse at submit, not at cell 1 of a 64-cell night. Most importantly, the
reference must enter `CellKey` and `completed_cells`, or a resumed reference
grid treats earlier text-only images at identical settings as done. Add
`--reference` in the same change.

**8. `backend/jobs.py:225` — an overnight grid started from the browser leaves nothing in the log, and no job carries a timestamp.** *(small)*
The server logs a job only when it breaks; there is no line at start, per cell,
per image or at completion. The CLI, for exactly this case, prints one line per
cell when stdout is not a tty — so the *headless* path is loggable and the
browser path, the one with the grid panel and the resume checkbox, is not.
`Job` has no timestamps at all, so `/api/jobs` cannot distinguish a sweep that
is progressing from one wedged on a hung load, and nothing records how long a
night took even though every image's `duration_ms` is stored.
*Caveat:* timestamps must be JSON-native floats — `snapshot()` is serialised by
a bare `json.dumps` on the SSE path, which would raise mid-job on a `datetime`.
Set `finished_at` inside `_finish()`, the one exactly-once terminal path, not at
the tail of `_run`, which a job cancelled while queued never reaches. `_run` has
no local `req`, and do not log a step count there — `total_steps` is the cell's.
Add a `last_progress_at` touched in `on_progress`, or "is it moving" still needs
two polls. Drop the UI ETA and `KREA_LOG_FILE` from scope: redirecting
`serve.sh` already captures these lines.

**9. `web/app.js:1068` — the grid spec lives only in the DOM.** *(small)*
There is no `localStorage` anywhere in `web/`, and nothing server-side holds a
`GridRequest` either. README documents Resume as "tick it and re-submit the same
grid" and the schema refuses one without an explicit seed — so continuing last
night means reproducing, by hand and exactly, a variable block, three axis
strings and a seed only recoverable by reusing an image. Any interruption that
outlives the tab costs the definition, and retyping one axis slightly
differently produces a *different* grid that resume cannot match, silently
re-rendering cells.
*Caveat:* two-phase restore — model-independent fields synchronously at init,
ahead of the sync functions so those light up from the restored values, and
steps/CFG/mu inside `applyDefaults` gated on the stored `model_id` matching, since
that id is not known until `/api/status` lands. Hooking the existing `input`
listeners misses most writes (`choose()`, `reuse()`, the dice button assign
`.value` programmatically). Version the key, wrap every access in try/catch, and
do **not** persist the Resume checkbox — a box that comes back ticked the next
evening silently skips cells on a grid the user did not mean to continue. Drop
"open the UI from another machine": `localStorage` is per-browser and
per-origin.

**10. `backend/generate.py:69` — no `--from-image`: the PNG's own metadata is write-only.** *(small)*
`save_image` writes a complete, machine-readable reproduction set into every PNG
and nothing in the repo ever reads either block back. The browser has Reuse from
the database; the CLI has no equivalent from either source. So the workflow that
starts from an image you already have costs a browser trip and six numbers
retyped by hand, each a chance to get one digit wrong — at which point the sweep
is comparing against a different image and nothing says so.
*Caveat:* placement is load-bearing — read the PNG *before* `apply_env`, or
`meta["model"]` cannot fill `KREA_MODEL_ID` and `--from-image` on a Turbo PNG
silently renders on FLUX while claiming to reproduce. Use `getattr(im, "text",
{})` (a JPEG has no such attribute) and `meta.get("job")`. The file's size can
only win when all four size arguments are None. Do not inherit `job_id` from a
`--reuse <id>` variant — display it, never reuse it. Land it with the
`--mu`/`--no-mu` fix, since a third mu source makes that silent discard worse.

**11. `backend/clear.py:55` — deletion is all-or-nothing.** *(medium)*
`clear.py` has three switches and `clear_history` is `DELETE FROM images` with
an optional `favorite = 0`; the HTTP side deletes one row at a time. Meanwhile
the project already knows how to name a subset precisely — `_split_search`
compiles `job:ab12cd seed:42 cfg:<=1` to SQL — and that machinery is read-only.
A 200-cell grid started with a typo in the prompt, the case the whole
resume/cancel design exists to survive, can only be removed by 200 confirmations
or by destroying the gallery. The realistic outcome is leaving them in, which
then poisons `--resume` and `step_cost_ms`.
*Caveat:* do not reuse the orphan sweep on the filtered path — a filtered clear
that also removes every untracked PNG is a new all-or-nothing hazard inside the
feature meant to remove one. Resolve to an id list in one query and delete by
id, preferring `DELETE … RETURNING filename` so a row committed while the user
was typing cannot lose its file. Accept only `key:value` terms and refuse
leftover free text: `list_images`' LIKE fallback changes the predicate's
semantics on any token with an odd quote, and a destructive filter resolved
through a fuzzy index should not be confirmed blind. `job:` and `model:` are
substring matches, so the preview must name what it matched. Keep the browser
out of scope.

**12. `backend/storage.py:143` — nothing can read the PNG metadata back: no import, no reindex, and the WSL and Windows galleries can never be merged.** *(medium)*
Everything an `ImageRecord` needs is recoverable from the file — only `favorite`
is not, because it is written to SQLite alone. Three consequences: krea.db is a
single point of failure for an otherwise self-describing gallery; WSL and
Windows keep deliberately separate indexes with no way to merge; and a row whose
file went missing can never be repaired. A `backend/reindex.py` in `clear.py`'s
shape — walk a directory, skip names already present (filename is UNIQUE, so it
doubles as an idempotent reindex), insert through storage so the FTS trigger
fires.
*Caveat:* read `Image.open(p).info["krea"]`, not `.text` — `.text` is a property
that calls `load()` and decodes every pixel (measured 5 ms vs 38 ms on a 2048²
PNG); the conclusion that no decode is needed is right, the API named does the
opposite. Do not call it `backend/import.py` (`from backend import import` is a
SyntaxError, so no test can follow the house style). Copy in with the same
`.part`-then-rename discipline, and compare against `outputs_dir` first so a
reindex-in-place does not copy a file onto itself. Parse the filename prefix as
UTC. `_page` orders `id DESC`, so a merged month lands above everything already
there whatever its timestamps.

**13. `backend/jobs.py:198` — the first run reads "waiting for the job ahead…" for the whole download, and there is no way to start a load from the UI.** *(small)*
`_run` awaits `_ensure_loaded()` before taking the gate with the job still
`queued`, so the stream says "waiting for the job ahead…" for the entire ~32 GB
download — while the top bar says "loading weights…", so the page contradicts
itself. `POST /api/model/load` exists and no UI element calls it, so the only
way to start the first download is to queue an image and the only way to retry a
gated-repo 403 is to queue another. The very first thing a new user sees after
their first Generate is a message saying they are queued behind work that does
not exist, and the natural reaction — reload, or restart — is exactly wrong.
*Caveat:* `cancel()` keys its immediate-finish path on `status == "queued"`, so
adding a `loading` status without widening that regresses Cancel-during-load
from instant to a multi-minute no-op. Gate the label on whether a load is
actually needed, or a job genuinely queued behind another gets the same mislabel
inverted. The Load/Unload button pair is optional and interacts with the
unload-during-load defect.

**14. `backend/grid.py:351` — the grid's seed axis is a count, not a list.** *(small)*
Every other axis is a spec string through `parse_axis`, which already handles
lists, ranges and de-duplication — seeds are the one axis that cannot be given
as a list, while the contact sheet already treats seed as a first-class axis it
can put on rows or columns. This is the second night of every two-night
investigation: night one finds that seeds 4471 and 8823 gave the composition you
want, and night two — those two crossed with a finer sweep — cannot be asked
for. The workarounds are two separate grids the sheet cannot join, or rendering
4353 seeds to reach the second one.
*Caveat:* `expand()`'s `total` multiplies by `seeds`, so replacing only the loop
lets a 64-value list queue 64× past `max_grid_images`. `_resume_needs_a_fixed_seed`
tests `seed is None`, so a resume fixed by the axis but with a blank base seed
is refused — the one case where resume is most clearly determinate. `describe()`
takes the count. And do not `wrap_seed` a listed value: the schema's own bounds
are what turn a typo'd `-5` into an error rather than a valid 9.2-quintillion
seed.

**15. `backend/backends/diffusers_backend.py:405` — on FLUX.1, real CFG is welded to the distilled guidance value.** *(medium)*
The backend sets both knobs from one number, so the only reachable
configurations are (3.5, off) and (g, g). The usual way to run true CFG on a
dev-family FLUX — guidance embedding near 1.0 while real CFG does the work at
3–5 — cannot be expressed, and neither can "keep the recommended 3.5 embedding,
add a mild real CFG of 1.5". Type a negative prompt at the default 3.5 and you
silently get guidance stacked twice at double the time per step, with one column
recording both values. CLAUDE.md states the mechanism correctly and then states
the coupling as if it were the only option; that sentence is the decision to
revisit.
*Caveat:* wider than it looks. `/api/status` cannot express the new state
(`cfg_threshold` answers 1.0 for FLUX.1, klein and the fallback alike), so
`describe()` needs a `true_cfg_supported` key merged the same way and both
threshold consumers must compare against the effective value. `cell_key` and
`completed_cells` must carry the column at the same rounding, plus the `krea`
chunk, the A1111 line and a filter. FLUX's `do_true_cfg` also requires a
non-empty negative prompt, so the value must stay gated on one. Ship the fourth
grid axis as a follow-up — it is fifteen more touch points.

**16. `web/app.js:307` — the browser can hold exactly one job, so the server's queue cannot be used from the UI.** *(medium)*
`startJob` opens with `if (busy) return;` and `setBusy(true)` disables both
submit buttons for the life of the job. The server was written for the opposite:
jobs wait on `_gate`, `cancel()` finishes a queued job on the spot "so
cancelling it does not first require the job ahead of it to end", `busy()` is
deliberately wider than `_gate.locked()`, and `/api/jobs` returns *every*
non-terminal job. The giveaway is the client's own "waiting for the job ahead…"
branch — a state the browser cannot produce for itself.
*Caveat:* change `resumeActiveJob` to attach to the oldest non-terminal job
first, or a reload shows "waiting" while the running sweep is invisible. `if
(busy) return` is also the only double-submit guard, so disable the button for
the duration of the POST instead. Do not call `setBusy(false)` between chained
jobs — it nulls `currentJob` and hides the bar; split "a job is being watched"
from "anything is queued". Fix the queued caption in the same change.

**17. `web/app.js:920` — the contact sheet never shows which cells you starred, and crops every cell it is meant to be comparing.** *(small)*
Triage works — a sheet cell hands the lightbox the whole sheet in reading order,
so the arrow keys and `f` walk and star it — but the result is invisible where
it would mean something: `renderSheet` never consults `rec.favorite`, though the
star badge already exists for gallery cards. So an interrupted pass over 500
cells restarts blind, and the conclusion — which row and column the keepers
cluster in — exists only in the user's head. Second, `object-fit: cover`
centre-crops every cell, so a portrait run compares the middle 68% of each frame
and hides the composition at top and bottom, which is exactly what a CFG or mu
axis moves.
*Caveat:* `.sheet-cell` has no `position: relative`, so sharing the card's
`::after` star would pile every badge at the top of the page. `setFavorite`
selects `.card[data-id]` only, so sheet cells need a `data-id` and a widened
selector — do *not* call `renderSheet()` on toggle, which rebuilds up to 1024
`<img>` nodes and resets the horizontal scroll on every keypress. Derive one
aspect ratio for the whole grid, since size is not a sheet axis and a free-text
search can mix sizes. Skip the per-cell hover star, or it repeats the
invisible-tab-stop defect at 1024 cells.

**18. `backend/storage.py:258` — `created_at` is recorded, indexed and never used.** *(small)*
No date key in `_FILTERS`, ordering by id, and the field appears nowhere in
`app.js` — not on the card, not in the sheet cell, not in the lightbox meta
line. So the only way to scope the gallery to one night is `job:<id>`, reachable
only by finding a card from that run and clicking its hover-only ⊞ button, and
NULL for every row written before that column existed. Two nights on the same
prompt are indistinguishable except by scroll position, and the `key:value` box
that answers every other question cannot answer the most common one.
*Caveat:* implement it as a half-open range, not a LIKE prefix — the `cast is
str` branch returns a substring match before any comparison is reached, a
non-str cast partitions `2026-09-06` on its own hyphen into a BETWEEN that
matches nothing, and a prefix LIKE cannot use the index. More importantly
`created_at` is UTC and an overnight run crosses midnight in every timezone, so
parse the term as a *local* date and convert — which also makes `date:today`
easy.

**19. `backend/storage.py:163` — no content hash, so nothing can tell you an axis produced identical images.** *(small)*
The table records what was asked for and never anything about what came out, so
"did this axis do anything?" is answerable only by eye over a 96 px grid. Not
hypothetical: a `{avoid}` variable in the negative prompt is a legal three-value
axis, and on klein — which has no `negative_prompt` at all — those three cells
run the same prompt, steps, seed and generator and produce three bit-identical
PNGs, while the preview reports "3 prompts" and triples the estimate. A 16-hex
sha256 of `image.tobytes()` costs a few ms against a 4–24 s generation and makes
"1024 images, 512 distinct — the mu axis changed nothing" free and exact.
*Caveat:* bit-determinism is an unverified premise the whole feature rests on —
two identical calls must produce identical pixels through quantized kernels with
components moving devices mid-forward. Verify with one two-cell grid first. Drop
the `ImageStat.stddev` half: a legitimately dark image has low stddev, so it is
a false-positive generator with no defensible threshold. `dupes:` does not fit
`_FILTERS` (it needs a GROUP BY … HAVING subquery) and a global one is useless;
scope the count per `job_id`. The higher-value companion is a preview-time
warning built from the capability flags already published.

**20. `backend/generate.py:338` — nothing coordinates the CLI with a running server.** *(medium)*
`generate.py` constructs its own backend and loads a second copy of the weights
into the same GPU, with no probe and no lock. The two processes already share
the SQLite gallery safely — WAL, a per-process write lock, `.part` renames — so
the database side of coexistence was thought through and the GPU side was not.
The server holds ~8 GB reserved in torch's caching allocator after its first
generation even under model offload, so a CLI sweep started against that spends
minutes loading and then OOMs on the first step, and the user's own mental model
("the CLI is the web app minus the web") invites it.
*Caveat:* scope to the probe and drop `--remote`, which is a separate large
piece. Probe `GET /api/status`, not a raw socket: the model is deliberately not
loaded at startup, so a listener alone is the ordinary harmless state and would
false-alarm every time. Refuse only when the state is ready or loading, name the
checkpoint the server holds, treat a timeout as busy, and place the check after
the `--dry-run` guard. The check is one-directional and blind across the
WSL/Windows boundary, so word it as advisory — and give the refusal its own exit
code, since the README pins the existing four.

**21. `backend/main.py:177` — no way to hand the GPU back mid-night.** *(medium)*
A job is running or terminal; `cancel()` is the only brake and it *ends* the
job, and unload is refused while any job exists. So while a 480-cell grid is
alive there is no operation in the app that gives the card back, even
temporarily — one person, one GPU, and the card that is eight hours into a grid
is also the card they want for twenty minutes. The machinery for a hold is
already there: `_generate` polls `cancel_requested` at the top of every cell,
and by that point `backend.generate()` has returned.
*Caveat:* judges recommend the cheap half only — a pause at the cell boundary
plus `torch.cuda.empty_cache()` returns nearly all VRAM under the documented
model-offload default, with a seconds-long resume and no `busy()` change. The
full unload-while-paused design needs a worker-written acknowledgement (never
the endpoint's flag) or an unload lands mid-denoise, and it only matters for
`KREA_OFFLOAD=none`, which CLAUDE.md already says does not fit these
checkpoints. Whatever lands, a bare `Event.wait()` deadlocks `shutdown()` and
makes `cancel()` a no-op on a paused job. Budget 100–150 lines across four
files, not 40.

**22. `backend/backends/diffusers_backend.py:199` — no LoRA loading, though all three families ship a LoRA mixin.** *(medium)*
`Krea2Pipeline`, `Flux2KleinPipeline` and `FluxPipeline` all mix one in, so
`load_lora_weights`/`set_adapters`/`unload_lora_weights` are on the object the
backend already holds. Style and subject LoRAs are the main way a local
generator becomes personal, and they are the one input class this app cannot
express: the user has a 200 MB LoRA on disk and the only way to use it is to
stop using this project. The grid makes it more valuable than usual, since scale
is a per-call setting and "the same prompt at strength 0–1×0.2" is exactly the
comparison a sweep is for.
*Caveat:* an fp8/int8/bf16-path feature — Nunchaku's quantizer is not trainable
and its linears are not `nn.Linear`, so refuse before the download the way
`_nunchaku_preflight` does. `peft` is a new dependency. The "adapters must
precede `enable_model_cpu_offload`" constraint is false (diffusers strips and
re-attaches the hooks), so hot-swap on the live pipeline is cheaper and safer
than baking the set into `load()`, which would create a second load path driven
from the job worker. Land the columns, the `krea` key and the `completed_cells`
key in the same change as the first working generation — images that do not
record which adapter made them corrupt Reuse and resume permanently. torchao +
PEFT is the unverified part; never merge on a quantized base.

**23. `backend/clear.py:49` — no running surface reports gallery size or free space.** *(medium)*
The only disk accounting in the project lives inside the destructive tool:
neither `/api/status` nor `/api/jobs` carries file count, bytes on disk or free
space, and `GridPreview` estimates a run's time but not its size. When the disk
fills the night dies at the first `image.save` and, per the cell-loop defect,
abandons every remaining cell. The panel already promises "about 6h20m"; "about
5.1 GB, 2.0 GB free" is the half that stops that.
*Caveat:* do not put `summarise()` on `/api/status` — the UI polls it every 3 s
and it globs and stats every PNG, so at 10k files that is a directory walk three
times a second on the event loop. `shutil.disk_usage` is one syscall and is fine
there; the file tally belongs on an on-demand endpoint. The bytes estimate is
the weakest third (PNG size varies with content far more than duration does), so
ship it under the same "no rows, no estimate" rule and drop it first.

**24. `backend/storage.py:325` — nothing can answer "which settings actually produced my favourites".** *(small)*
The favourite flag is queryable only one value at a time, and there is no
aggregation anywhere in the project. The naive count would also mislead, since
it rewards whichever setting you used most rather than the one that works; what
is wanted is the keep *rate*, and every input is in the table. One query behind
`python -m backend.stats`, with `HAVING made >= 5` so a lucky 1-of-1 does not
take first place.
*Caveat:* the all-time table is confounded — over months it rewards whichever
settings were in use while the prompts happened to be good — so default it to a
job or grid scope, where `expand()` guarantees the axes were crossed against the
same prompts and seeds, and present all-time as indicative. Group on the same
six-decimal rounding `completed_cells` uses, or one CFG splits into two buckets
after a round trip through REAL. Include size in the grouping, and call the
column *starred*, not *kept*: nothing records a rejection, so an untouched night
reads 0% rather than unknown.

**25. `tests/test_klein.py:45` — the pipeline facts the UI and CLI hang off are asserted against hand-written stubs, never the real classes.** *(small)*
`cfg_threshold()` and `negative_prompt_supported` are derived entirely from
`inspect.signature(pipe.__call__)`, and `_PROFILES` hard-codes the same two
answers per checkpoint for the unloaded case — so the profile's guess and the
pipeline's answer have to agree, and today only a human keeps them in step. The
real classes need neither weights nor a GPU. About 20 lines, parametrized over
five id→class pairs; all ten assertions are green today.
*Caveat:* `cfg_threshold` returns `None` while `_pipe` is None, so the test must

free: importing the four pipeline classes adds ~2 s to a 9 s suite.

**26. `tests/test_gallery.py:22` — the PNG metadata, the only copy of the reproduction set outside SQLite, is never read back.** *(small)*
The existing test checks only that the file exists and no `.part` is left, so
the metadata dict is maintained by hand against a schema that has already gained

*Caveat:* write it as a key-set *equality*, not a presence check, so adding a

`test_gallery`'s helper accepts neither mu nor `job_id`, so use `test_storage`'s

**27. `backend/launch.py:62` — nothing joins the checkpoint catalogue to the profile table.** *(small)*
`CHECKPOINTS` and `_PROFILES` are two hand-maintained lists joined only by
substring matching, and nothing checks the join. All 15 repos resolve correctly
today, so this is coverage rather than a live bug — but `Checkpoint.summary()`
renders `defaults_for(self.repo)` straight into the menu, so an entry that
missed every token prints the fallback's "28 steps, CFG 3.5" in the same column
as a real profile. Add `Checkpoint('Krea 3 Turbo', …)` and forget the profile
row and a distilled 4-step model runs at 28 steps with the suite green;
`krea/Krea2-Turbo` (same model, no dash) already resolves that way.
*Caveat:* detect the fallback by *identity*, not by value — the flux profile is
value-identical to `_FALLBACK` in every non-hints field, so the obvious
inequality assertion fails on the shipped default for 3 of 15 parameters.
Identity alone is also insufficient (a hypothetical FLUX.3 entry matches the
`flux` token), so make pinned per-entry expectations the primary check and drive
them from `CHECKPOINTS`. Drop the "(unrecognised)" suffix on `summary()`: once
the test exists it can never fire, and it would overrun the menu's column.

**28. `web/app.js:450` — a running sweep reports no elapsed time and no ETA.** *(small)*
`snapshot()` carries counters and no timestamp, so the server cannot supply one
either, and a clean `done` clears the text and shows no summary — a finished
grid leaves the panel indistinguishable from an idle page. Everything needed is
already used *before* the run starts. At 03:00 on "run 712/1024" the user cannot
tell whether the grid finishes at 06:00 or at noon, and the counter hides a run
that has slowed: 712/1024 looks like 70% whether the rest takes one hour or
twelve.
*Caveat:* get the unit right — `duration_ms` is per image, so `step_cost_ms` is
per-image-per-step while the job's own per-cell elapsed is a whole-cell cost;
mixing them is a silent factor of `num_images`. Prefer the job's own finished-cell
timings, which need no DB access from `snapshot()` and actually track the
slowdown this is meant to reveal. Stamp `finished_at` in `_finish` and a
separate started timestamp when status flips to running. The `done` summary has
nowhere to go as sketched — `#progress-text` is inside the element `setBusy`
hides.

**29. `backend/backends/diffusers_backend.py:354` — the step callback already receives the latents; a live preview would cost one small matmul per step.** *(medium)*
`_step_end` is handed `cb_kwargs["latents"]` every step and throws it away, and
the whole transport to the browser is already built. A real `vae.decode` per
step is out of the question under model offload, but the standard linear
approximation gives a blurry, compositionally accurate thumbnail for
microseconds and no device movement. A 50-step klein-base or 28-step FLUX render
is 30–60 seconds of a bar with no picture behind it; seeing composition at step
3 lets a bad prompt be cancelled in five seconds, and cancellation already lands
within one step, so the two compose.
*Caveat:* an exception out of `_step_end` unwinds the denoising loop — that is
how `Cancelled` is implemented — so the whole block must sit in a try/except
that logs once and disables itself: a shape mismatch must cost a preview, not a
64-cell night. `_unpack_latents` is not one API (FLUX's is a 4-arg staticmethod,
Krea2's a 3-arg instance method returning 5-D, klein has none reachable from the
callback), so ship for FLUX.1 and Krea 2 only. Key the factor matrix on (VAE
class, latent channels) — FLUX.1's VAE is the generic `AutoencoderKL` that
4-channel SD VAEs also use — and match each family's normalisation, or the
preview is a confidently wrong-coloured blur. The callback hands you x_t, not
x_0. The matrices cannot be validated in CI.

**30. `backend/jobs.py:251` — a run cannot be given a wall-clock budget.** *(medium)*
The cell loop breaks on one condition and `GridRequest` has no notion of time,
so the night is sized by hand from an estimate. This is the one case CLAUDE.md
deliberately engineered for and then left unreachable: seeds are outermost
specifically so that a night ending early "has finished every parameter
combination for the seeds it reached" — and every listed way of ending early is
an accident. With a budget you over-provision on purpose and take what the night
reaches.
*Caveat:* value is contingent — this project has no other workload on a
schedule, so it buys tidier sizing rather than a new capability. If built, skip
the new terminal status (a state not in `_TERMINAL` means `active()`/`busy()`
never let go and unload 409s for the session); setting `cancel_requested` at the
deadline reuses the existing path. Plumb the deadline through `submit_cells`,
not `job.request`, since GridRequest-only fields are dropped when cells are
built. The break is at cell boundaries, so it means "start no cell after". And
the payoff silently does not happen if the grid was submitted with an empty seed
box, since resume then refuses to continue it.

**31. `web/app.js:839` — a grid cannot be exported as one contact-sheet image.** *(medium)*

*Caveat:* judges settled on client-side (`canvas` + `toBlob` + a download link):

**32. `backend/backends/diffusers_backend.py:72` — dead state.** *(small)*
